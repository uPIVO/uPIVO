# ITD-86 — Пользовательские интересы и расчёт релевантности

**Статус:** спецификация к реализации\
**Связанная задача:** [ITD-86](https://yzcjhacj.yougile.com/team/74c58e471796/#ITD-86)\
**Соседняя задача:** [ITD-85 — завершение единого конвейера](https://yzcjhacj.yougile.com/team/74c58e471796/#ITD-85)\
**Репозиторий:** uPIVO/uPIVO\
**Дата решений:** 2026-10-27

## 1. Цель

Дать пользователю возможность необязательно задать **глобальный** список интересов в свободной текстовой форме; хранить список в PostgreSQL, управлять им через API и использовать его как вход уже реализованной AI-оценки персональной релевантности единицы контента.

Примеры отдельных интересов: «ИИ-агенты для программирования», «Новые модели OpenAI», «Электромобили». Это текстовые формулировки, а не жёсткий словарь категорий. Один список применяется ко всем подключённым источникам. Интересы **не являются** папками `folders` или существующими `topics` из `/api/users/{user_id}/topics` и не изменяют их поведение.

**Ключевое продуктовое решение:** пользователь может иметь ноль интересов. Тогда материалы его включённых источников доступны без фильтрации по персональной релевантности; существующая суммаризация, группировка в кластеры, ограничение объёма дайджеста и прочие правила отображения продолжают действовать. Ноль интересов не означает «релевантность = 0»: **оценка не нужна и AI-вызова нет**.

Такой режим в будущем позволит стартовать без обязательного заполнения интересов и постепенно адаптировать их по реакциям пользователя: лайкам/дизлайкам публикаций или упоминаемых в них тем. **Автоматическое обучение интересов и обратная связь не входят в ITD-86.**

## 2. Границы задач и зависимости

### ITD-86 (эта работа)

- PostgreSQL-модель интересов и миграция Alembic.
- CRUD API и сервис для получения полного, детерминированного списка интересов конкретного пользователя.
- DB-backed интеграционный путь к существующему `RelevanceService` / `ContentUnitAnalysisUseCase`: получать интересы из БД, оценивать допустимые единицы контента и сохранять результат через существующий `user_item_scores`.
- Обработка нулевого списка без ошибки или платного вызова.
- Интерфейс проверки просмотренности, позволяющий позже подключить существующий/будущий механизм учёта просмотров без переписывания логики персональной оценки.
- Экономный пересчёт ещё не просмотренных единиц после изменения интересов **при наличии подключённого источника сведений о просмотренности**; без него не запускать массовый ретроспективный пересчёт. Учесть гонки и повторные запуски.
- Тесты контракта, хранения и интеграции; точки подключения для ITD-85.

### ITD-85

- Оркестрация конвейера после сбора, нормализации, извлечения сущностей и кластеризации.
- Автоматический запуск общей суммаризации и важности, затем вызов персональной оценки для подходящих пользователей **через интерфейс, реализованный ITD-86**.
- Выбор единственной единицы анализа: одиночный `FeedItem` или `ContentCluster`.
- Фоновые задачи, ретраи и общие статусы обработки.

**Условие стыковки:** ITD-86 не запускает заново сбор/кластеризацию и не дублирует конвейер; ITD-85 после готовности выжимки вызывает предоставляемый сервис оценки для заинтересованных пользователей. Работу по этим задачам можно вести независимо, затем согласовать вызовы при интеграции веток.

### За пределами обеих задач в данном объёме ITD-86

Изменение алгоритмов выбора, фильтрации и сортировки ленты/дайджестов; веса `rank_score`, пороги релевантности, персонализация по лайкам/дизлайкам, UI и онбординг, аутентификация. Хранение оценок не должно незаметно поменять существующую логику показа.

## 3. Зафиксированные пользовательские правила

1. **Форма интереса:** один произвольный непустой текст, без обязательного отдельного названия и описания.
2. **Область:** один список на пользователя, без привязки интересов к отдельным источникам, папкам и дайджестам.
3. **Пустой список:** штатное состояние. Суммаризированные материалы из включённых источников по-прежнему доступны; персональная оценка не запускается. Не подменять отсутствие оценки нулём.
4. **Момент оценки:** после появления **актуальной готовой выжимки** единицы контента. Автоматический запуск этого этапа в полном конвейере принадлежит ITD-85.
5. **Подходящие источники:** оценка для пользователя проводится только по контенту хотя бы одного его включённого `user_sources`; не делать вызов для всего глобального каталога.
6. **Единица оценки:** если `FeedItem` входит в кластер, оценивать готовую общую выжимку `ContentCluster`, **не** каждую входящую публикацию. Если вне кластера — выжимку `FeedItem`. Одна оценка на пару «пользователь + единица контента».
7. **После изменения интересов:** когда механизм просмотренности доступен, актуализировать только контент, который он считает **не просмотренным** пользователем. Просмотренные единицы, ранее созданные дайджесты и их snapshots не пересчитывать/не переписывать из-за смены интересов. Пока сведений о просмотрах нет, массовый пересчёт существующих единиц не запускать — новый контент всё равно оценивается по действующим интересам.
8. **Нет интерпретации темы как ключевого слова:** использовать существующую семантическую AI-оценку для **всего** списка интересов, а не набор самостоятельных порогов или сравнений строк.

## 4. Существующие компоненты — использовать, а не переписывать

Проверено по состоянию `main` на 2026-10-27:

- `backend/app/ai/dto.py`: `RelevanceInput(summary, interests: list[str])` требует непустой список; `RelevanceResult.relevance` лежит в диапазоне 0..1.
- `backend/app/ai/service.py` + `backend/app/ai/jev.py`: существующий AI-адаптер.
- `backend/app/ai/analysis_policy.toml`: соответствие хотя бы одному интересу достаточно; случайное упоминание недостаточно.
- `backend/app/services/analyze_feed_item.py`: `ContentUnitAnalysisUseCase`, операции `summary`, `importance`, `relevance`, `all`; сейчас интересы передаются извне.
- `backend/app/ai/repository.py` + `backend/app/ai/analysis_metadata.py`: запись оценки и fingerprints входного контента, выжимки и списка интересов; защита от устаревших результатов обработки контента.
- `backend/app/models/user_item_score.py`: одна таблица `user_item_scores` для одиночного материала или кластера, с взаимоисключающими `feed_item_id` и `cluster_id`.
- `backend/app/api/users.py`: существующий стиль API по `user_id` в URL, без готовой авторизации.
- `backend/app/services/feed.py`, `backend/app/services/digest.py`: возвращают карточки ленты и дайджеста; сейчас не отслеживают факт выдачи каждой единицы контента. `digests.items_snapshot` хранит историческую форму карточек.

**Важное ограничение:** не изменять существующий `RelevanceInput` так, чтобы пустой список передавался в AI. Пустота обрабатывается уровнем выше как `skip`. Существующий CLI с явным JSON-файлом интересов сохранить рабочим; новый DB-backed путь не должен ломать прежние тесты и примеры.

## 5. Модель данных

### `user_interests` — новая таблица

Минимальный контракт:

| Поле | Назначение |
| --- | --- |
| `id` | PK в стиле существующих ORM-моделей |
| `user_id` | обязательный FK `users.id`, `ON DELETE CASCADE` |
| `text` | непустой текст интереса |
| `created_at` | дата создания |
| `updated_at` | дата изменения, если менялся |

Индекс по `user_id`. Список интересов читается в устойчивом порядке (например, по `id`), и **именно такой порядок** участвует в fingerprint. При равнозначном чтении двух одинаковых наборов fingerprint должен совпадать; перестановка, не вызванная изменением интересов, не должна провоцировать переоценку.

Правила записи: trim внешних пробелов; отвергать пустую/пробельную строку; предотвращать повтор одинакового текста в пределах одного пользователя (регистр и несущественные крайние пробелы не должны порождать новую запись). Обеспечить уникальность при конкурентных запросах на уровне БД, а не только предварительным SELECT. Никаких глобально общих interest-объектов не нужно.

**Не добавлять** связи между `user_interests` и `folders`, `topics` или `sources`. Существующую `user_item_scores` использовать повторно, без новой таблицы оценок по каждому интересу.

### Подключение будущего механизма просмотренности — без его реализации в ITD-86

Сейчас backend не имеет надёжного признака «пользователь просмотрел единицу контента». **Не вводить отдельную таблицу доставок/показов, не помечать все возвращённые API карточки как просмотренные и не изменять существующие API ленты/дайджестов ради такого учёта.** Карточка, полученная сервером, не обязательно была реально прочитана/увидена пользователем.

Вместо этого определить узкую абстракцию чтения статуса, например:

```python
class ViewedStatusProvider(Protocol):
    def was_viewed(self, user_id: int, kind: Literal["feed_item", "cluster"], unit_id: int) -> bool: ...
```

Точное имя и способ внедрения (зависимость, адаптер, протокол репозитория) выбирает реализация. Важно отделить **правило отбора кандидатов на пересчёт** от **источника признака просмотра**. Если при внедрении механизма просмотров будет удобнее пакетный интерфейс, допускается пакетная проверка во избежание N+1 SQL-запросов.

Контракт:

- `True`: пользователь просмотрел единицу; при изменении интересов её **не пересчитывать**.
- `False`: единица не просмотрена; при изменении интересов её **можно пересчитать**, если выполнены остальные условия.
- **Провайдер не подключён:** статус **неизвестен**; нельзя трактовать его как `False` и пересчитывать всё. Система **не запускает массовую ретроспективную переоценку** до появления интеграции.
- Определение «просмотрено» и запись событий просмотра в БД — ответственность будущей задачи. Когда она появится, её механизм должен подключаться через этот интерфейс без изменения AI-алгоритма.
- Для кластерной единицы всегда используется `kind="cluster"`; сопоставление событий просмотра отдельных публикаций с просмотром кластера — обязанность будущего адаптера/продуктового решения, а не предположение ITD-86.

Тесты должны использовать подставной (fake) провайдер статусов и проверять обе ветви — `True` и `False`, а также поведение при отсутствии провайдера.



## 6. API управления интересами

По аналогии с существующими источниками пользователя; базовый префикс — `/api/users/{user_id}/interests`:

| Метод и путь | Результат |
| --- | --- |
| `GET /` | список интересов пользователя, включая допустимый `[]` |
| `POST /` | добавить один интерес по `{"text": "..."}`, ответ 201 с созданной записью |
| `PATCH /{interest_id}` | заменить текст интереса, вернуть обновлённую запись |
| `DELETE /{interest_id}` | удалить интерес, ответ 204 |

Ответ объекта: `id`, `user_id`, `text`, `created_at`, `updated_at`. Отсутствие пользователя или интереса **данного** пользователя — 404; невалидный текст — 422; дубликат — 409 без создания второй строки. PATCH с тем же нормализованным текстом не должен запускать повторный пересчёт.

На данном этапе авторизация не реализована и **не добавляется** этой задачей; `user_id` соответствует текущим API, однако сервис и запросы обязаны проверять принадлежность данных пользователю, не выдавая чужие интересы. После внедрения аутентификации маршруты должны привязываться к авторизованному пользователю.

## 7. Интеграция оценки

### Программный контракт ITD-86 → ITD-85

Предоставить явный backend-интерфейс (названия методов выбирает реализация):

- `load_user_interests(user_id) -> list[str]`: детерминированный порядок.
- `score_user_content_unit(user_id, kind, unit_id)`: загрузить актуальную единицу и список интересов из БД; проверить право пользователя на единицу через включённые источники; пропустить AI, если список пуст или нет актуальной выжимки; иначе использовать существующие `RelevanceService`, `ContentUnitAnalysisUseCase` и `user_item_scores`.
- `score_content_unit_for_eligible_users(kind, unit_id)`: определить пользователей, у которых включён хотя бы один источник этой единицы и есть интересы, запланировать/выполнить персональные оценки **в фоне**, без N платных запросов внутри HTTP-запроса. Этот интерфейс вызывает ITD-85 после готовности выжимки.
- `recalculate_unviewed_for_user(user_id, viewed_status_provider)`: готовая к подключению точка пересчёта после изменения интересов; выбирает только кандидатов с `was_viewed(...) == False`. Если провайдер пока отсутствует, **не** ставит в очередь исторические единицы. Не подменять отсутствие провайдера константой `False`.

Подтвердить договором тестов: кластер, у которого хотя бы одна публикация относится к подключённому источнику, оценивается как кластер, включая случай, когда другие члены глобального кластера пришли из источников, не подключённых пользователем. Используется уже сформированная **общая** выжимка кластера; специально пересуммаризировать под пользователя не требуется. Изолировать персональные оценки пользователей.

Если пользователь отключил источник, новые оценки для контента **исключительно** из него не запускать. При повторном включении источника или подключении нового использовать ту же точку оценки новых материалов; ретроспективно переоценивать только единицы, признанные непросмотренными подключённым `ViewedStatusProvider`. При отсутствии провайдера не запускать массовый пересчёт истории. Интеграция с операциями подключения источников должна оставаться узкой и не изменять глобальные записи публикаций.

### Очередность и отказоустойчивость

1. Общая выжимка должна быть актуальна; персональная оценка не заменяет суммаризацию.
2. Общая важность остаётся независимой от конкретного пользователя и интересов.
3. Для нулевого списка `relevance_score` логически отсутствует; не вызывать `JevRelevanceAdapter` и не создавать фиктивную оценку 0.
4. Повтор операции с той же выжимкой, тем же каноническим списком интересов и тем же актуальным результатом не должен заново обращаться к AI.
5. Если список интересов изменился в ходе внешнего AI-вызова, **не сохранять** ответ для старого набора как `current`. Прежде чем подтвердить запись, в транзакции проверить актуальный fingerprint списка интересов пользователя; устаревший ответ не должен попасть в действующую оценку. Сохранять существующую защиту по fingerprint выжимки.
6. Ошибка одного пользователя не должна препятствовать общей обработке материала или оценке других пользователей. Временная недоступность AI не должна скрывать публикацию и не должна превращаться в `relevance_score=0`.

## 8. Изменение списка и экономный пересчёт

Триггеры — успешные POST/PATCH/DELETE **с фактическим изменением** текста/набора. Обновление интереса `A` на `B` меняет **весь список** входных данных одной общей оценки, а не только новости, связанные со словом `A`.

**Новая целевая схема (когда появятся сведения о просмотрах):**

1. После изменения интересов фоновый обработчик получает статус просмотренности через подключённый `ViewedStatusProvider`.
2. Селектор находит единицы из **сейчас включённых** источников пользователя с готовой актуальной выжимкой, для которых `was_viewed(user_id, kind, unit_id) == False`.
3. Повторно оцениваются только эти ещё не просмотренные единицы. Если публикация входит в кластер, работает только кластер; обработка дедуплицирована по паре пользователь–единица–версия интересов.
4. Просмотренные единицы не переоцениваются из-за изменения интересов. Исторические дайджесты и `items_snapshot` не редактируются.
5. Работы выполняются фоново и идемпотентно, перед записью актуальность интересов и выжимки проверяется повторно. Старый ответ от AI не может перезаписать актуальный.

**Что обязательно работает уже в ITD-86 без механизма просмотров:**

- CRUD и хранение интересов, загрузка текущего полного списка, оценка **новых единиц контента** по актуальным интересам после появления их выжимок (через ITD-85).
- После изменения интересов актуальная версия входного списка распознаётся по fingerprint; устаревшие персональные оценки нельзя интерпретировать как `current`. Существующую историю результатов допустимо сохранять.
- **Не запускать массовую переоценку ранее обработанных материалов**, потому что пока неизвестно, какие из них просмотрены. Это осознанный компромисс в пользу экономии AI-вызовов, а не утверждение, что все старые материалы просмотрены.
- После подключения реального `ViewedStatusProvider` обработчик изменения интересов начнёт использовать описанный выше отбор по непросмотренным — без переделки самого AI-расчёта. Не требуется пересчитывать историю лишь из-за факта подключения провайдера.
- При полном удалении интересов платных пересчётов нет. Для нового контента оценка пропускается; сохранённые оценки с неактуальным fingerprint не должны использоваться как оценки для пустого списка.
- При повторном появлении интересов (`[]` → непустой список) новые единицы оцениваются по ним; ретроспективная переоценка — только при наличии статуса просмотренности.

Не вводить произвольный срок давности (`7 days` и т. п.) вместо данного правила. Если при дальнейшей разработке потребуется ограничить горизонт пересчёта, это отдельное продуктовое решение.

### Взаимодействие с лентой/дайджестом

**Не изменять существующие маршруты ленты/дайджеста** ради фиксации просмотров и не добавлять фиктивное понятие «просмотрено при выдаче из API». Не добавлять в ITD-86 фильтрацию по `relevance_score`, не менять сортировку, лимит дайджеста или исторические snapshots. Реализация записи факта просмотра и применение оценки при отборе — самостоятельные задачи.

## 10. Приёмочные сценарии

- GET для нового пользователя возвращает `[]`, источники и лента продолжают работать без персонального AI-вызова.
- POST, GET, PATCH, DELETE работают; два одинаковых интереса нельзя создать, включая конкурентные запросы; чужой `interest_id` недоступен.
- Пользователь с двумя интересами получает **одну** оценку выжимки по полному списку; оценка не обязана быть низкой, если подходит только один интерес.
- Одиночный материал из активного источника получает score; материал из чужого/отключённого источника — нет; кластер оценивается один раз на кластер, а не по членам.
- Для одинакового набора интересов и выжимки повторный вызов использует актуальный результат без второго внешнего запроса.
- С подключённым fake `ViewedStatusProvider` изменение интересов переоценивает только единицы, для которых провайдер вернул **не просмотрено**; просмотренные единицы и snapshots не переписываются.
- Если провайдер отметил кластер просмотренным, изменение интересов не запускает пересчёт этого кластера или его отдельных участников.
- Если провайдер **не подключён**, изменение интересов не инициирует массовый ретроспективный пересчёт; новые единицы после появления выжимки получают оценку по новым интересам; фиктивных записей о просмотренности нет.
- При переходе к пустым интересам новые платные вызовы прекращаются; прежние оценки не участвуют в интерпретации персональной релевантности новых или подлежащих переоценке единиц контента.
- При гонке «изменение интересов во время AI-запроса» устаревший результат не становится `current`.
- Упавший AI-провайдер или неготовая выжимка не ломает CRUD и не приводит к ложному отрицательному score.
- Существующие тесты суммаризации, оценки важности, кластеризации, feed/digest и ручного CLI продолжают проходить.

## 11. Обязательные пояснения в **итоговом PR после реализации**

В описание финального PR обязательно вынести **отдельными пунктами**, а не оставлять только в этой спецификации:

1. **Необязательные интересы:** без явных интересов пользователь видит доступные суммаризированные новости из своих источников, без персональной фильтрации. Это осознанная подготовка к будущей персонализации по лайкам/дизлайкам как целых постов, так и тем внутри них; сами реакции/обучение этим PR не реализуются.
2. **Экономный пересчёт:** после изменения интересов планируется переоценивать только не просмотренный пользователем контент. Пока механизм просмотренности отсутствует, уже обработанные материалы массово не пересчитываются; новые оцениваются с актуальными интересами.
3. **Расширяемость:** в ITD-86 создан интерфейс `ViewedStatusProvider` для будущего источника статуса просмотра. **Учёт просмотров и фиксация выдачи карточек сейчас не реализуются**. После подключения провайдера селектор сможет исключать просмотренные единицы без переписывания AI-расчёта.
4. **Граница с ITD-85:** ITD-86 даёт данные и механизм персональной оценки; ITD-85 запускает его в автоматическом конвейере после общей выжимки. Персональное ранжирование и фильтрация ленты/дайджеста не реализованы здесь.
5. **Проверки:** перечислить миграцию, тесты и взаимодействие с изменениями ITD-85.

**Этот первый коммит содержит только спецификацию. PR сейчас не создавать**: локальный агент должен реализовать её в этой ветке, затем оформить итоговый PR с указанными пояснениями.
