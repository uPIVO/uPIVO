# ITD-84 — Автоматический сбор публикаций через Celery

Статус: **реализовано (БД-задачи, расписание, блокировка, полный автоматический
AI по решению от 2026-10-29 без контроллера расходов); учёт и бюджеты — будущая
работа** — см. раздел 8.
Зависимость: ITD-85, PR #18 (`feature/ITD-85-ai-pipeline`), поверх ITD-86, PR #13. База этой ветки — ITD-85; будущий PR ITD-84 должен первоначально целиться в `feature/ITD-85-ai-pipeline` и после её слияния обновить base.

## 1. Цель

Без ручной команды регулярно собирать новые публикации из **всех уникальных источников, включённых хотя бы у одного пользователя**, затем запускать общий конвейер:
```text
Celery Beat
    ↓ расписание
Redis (broker)
    ↓
Celery Worker: scheduled shared pipeline
    ↓
sync_active_sources(): Telegram / Reddit / YouTube / Habr
    ↓ commit в PostgreSQL
normalize_pending → extraction of entities → cluster_feed
    ↓ commit
run_common_analysis: Summary → Importance → processed
    ↓ enqueue relevance.score_content_unit_for_eligible_users
Redis → Celery Worker → Relevance (Jev, per user) → user_item_scores
```

Общий сбор и Summary/Importance **не выполняются для каждого пользователя отдельно**. Одно и то же сообщество / канал собирается один раз за проход; кластер — одна единица общего AI-анализа. Relevance — персональный классификатор на Jev, отдельно по пользователю. Никакой новой AI-классификации в ITD-84 не требуется.

## 2. Проверенные существующие компоненты и ограничения

- `backend/app/services/source_sync.py`: `sync_active_sources()` уже выбирает DISTINCT `Source.id` через включённые `UserSource` и вызывает существующие `sync_sources()`/`sync_source()` с коннекторами Telegram, Reddit, YouTube, Habr. Результат `SourceSyncResult` различает `collected`, `empty`, `skipped`, `failed`; ошибка одного источника не должна останавливать остальные.
- `backend/app/pipeline/run.py`: `run_pipeline(identifier, ...)` пока привязан к одному пользователю **только на стадии сбора**; затем глобально вызывает `_normalize_and_cluster()` и `run_common_analysis()`. Не делать цикл по всем пользователям с `run_pipeline(user)`: он повторит глобальные этапы и сбор.
- `backend/app/pipeline/analysis.py`: `run_common_analysis(..., ai_limit=DEFAULT_AI_LIMIT)`, текущий `DEFAULT_AI_LIMIT=50`. Цикл последовательный, не batch-пакет из 50 статей. Summary — один запрос на одиночный FeedItem или на кластер как целое; Importance — один запрос Jev с несколькими вопросами; персональная Relevance — отдельные фоновые запросы.
- `backend/app/workers/celery_app.py`: Redis уже указан как broker; `include=["app.workers.tasks"]`; `beat_schedule={}` пока пустой.
- `backend/app/workers/tasks.py`: уже определены персональные Celery-задачи `relevance.*`. Учитывать их при регистрации новых задач; не ломать существующий worker.
- `docker-compose.yml`: сервисы `worker` и `beat` уже входят в Compose profile `workers`, но включаются только при `docker compose --profile workers up -d --build`. Профиль — именованная группа сервисов, не число воркеров.
- `backend/app/ai/dto.py` и провайдеры: Summary может иметь `usage` и `cost_usd` из OpenRouter; Jev Importance/Relevance возвращает `usage` токенов, но не вычисляет/сохраняет стоимость USD. Сейчас нет полноценного журнала расходов, глобального бюджетного контроллера или ежедневной пользовательской квоты.

## 3. Изменения в рамках ITD-84

### 3.1. Общий entrypoint, без дублирования pipeline

Выделить переиспользуемую оркестрацию глобальных стадий в публичный сервис (например, `run_shared_pipeline`):
1. `sync_active_sources` — единичный обход всех активных уникальных источников, с результатами по источникам;
2. нормализация всех накопившихся `pending`, извлечение сущностей и кластеризация — по существующим методам, commit перед внешним AI;
3. общий `run_common_analysis` на нуждающемся в анализе backlog, а затем существующая постановка Relevance.

Ручной `run_pipeline(--user ...)` продолжает собирать только включённые источники выбранного пользователя, но делит **те же** глобальные последующие стадии с автоматическим путём. Сохранить CLI, `--dry-run`/`--fixture` и их гарантии отсутствия платных вызовов. Существующие коннекторы и семантику нормализации/кластеризации не переписывать.

### 3.2. Celery Beat и Worker

- Добавить задачу, например `pipeline.run_scheduled`, которая вызывает асинхронную глобальную оркестрацию через `asyncio.run(...)` внутри синхронной Celery-задачи и возвращает компактную сериализуемую статистику.
- Зарегистрировать задачу в существующем Celery app и настроить `beat_schedule`: интервал задаётся настройкой/переменной окружения; **30 минут — начальная рекомендация, не фиксированное бизнес-правило**. Часовой пояс задавать явно; в Celery использовать UTC, если не согласовано иное.
- По расписанию Beat **только отправляет** задачу брокеру, Worker **исполняет** её. Relevance-задачи остаются независимыми, их завершение не блокирует окончание общего прохода.
- Автоматический проход вызывает существующий общий AI-этап (`run_common_analysis`) и его штатную асинхронную постановку персональной оценки. Решением продукта от 2026-10-29 полный автоматический AI разрешён без контроллера расходов; флаг `SCHEDULED_PAID_AI_ENABLED` (по умолчанию `true`) при `false` оставляет только бесплатные стадии, без AI и постановки Relevance — см. 4.1.
- Необязательный `SCHEDULED_PIPELINE_SOURCE_LIMIT` передаётся как `limit` сбора и нормализации (`None` по умолчанию — обычное production-поведение). Это операционный предел публикаций на источник, а не `ai_limit` и не денежный бюджет; AI-этап по-прежнему идёт по всему backlog.
- Не стартовать `beat` в нескольких контейнерах с одинаковым расписанием без координации: иначе будут дублирующиеся постановки. В Compose — один экземпляр Beat на расписание.
- Существующий профиль `workers` сохранить; добавить корректную зависимость готовности Redis/PostgreSQL/миграций для scheduled worker и настройку перезапуска при сбое. Обновлять worker и pipeline согласованно, учитывая их общий формат AI metadata.

### 3.3. Конкурентность, повторы и восстановление

- Одновременно выполнять не более **одного полного общего прохода** среди всех воркеров/хостов. Перед началом использовать межпроцессную блокировку (кандидат: session-level PostgreSQL advisory lock на выделенном соединении; **не** длинная транзакция). При занятом lock — явный `skipped_locked`, без ожидания очередного полного запуска.
- Lock должен освобождаться при успешном завершении и падении исполнителя; проверить поведение при разрыве подключения и при его повторном получении.
- Частичная ошибка одного источника не отменяет успешный сбор других и не должна уничтожать сохранённые публикации. Ошибки AI/Redis отражать отдельно; накопленный backlog обрабатывать при следующем проходе. Готовые и актуальные результаты переиспользовать, не платить повторно.
- Никакой Redis-only блокировки без продуманного срока жизни/heartbeat. Потребление Celery task не гарантирует exactly-once: идемпотентность обеспечивается контрактами БД и проверками состояния, а не одним фактом постановки.
- Не держать транзакции БД открытыми во время Telegram/Reddit/YouTube/Habr или AI HTTP-вызовов. Ограничения внешних API, таймауты и контролируемые повторы сохранить/добавить по необходимости.

### 3.4. Наблюдаемость и ручной запуск

- Логировать id запуска, trigger (schedule/manual), начало/конец, длительность, число выбранных источников/публикаций/кластеров, поисточниковые ошибки, результаты AI, число задач Relevance, причины пропусков (`locked`, `paid_ai_disabled`, `disabled`).
- Параметры расписания и включения стадий должны быть видны в документации и конфиге, не требовать править код. Сохранять существующий диагностический CLI.
- На реальном Docker Compose проверить поднятие Beat + Worker, автоматическую постановку, работу через Redis и PostgreSQL, а не только mock-`delay()`.

## 4. Денежные ограничения: согласованная архитектура и граница ITD-84

**Изменение требований (2026-10-29, явное решение Denis):** продукту нужен
**полный автоматический pipeline**, финансовый контроллер пока не добавляется,
расходы без жёсткой денежной квоты допустимы. Поэтому автоматические
Summary/Importance/Relevance включены без контроллера расходов, а подсистемы
учёта и бюджета ниже остаются полезной архитектурой **будущей** отдельной работы.
Жёсткой денежной квоты сейчас нет; это осознанное состояние, а не забытая защита.

**Не считать `ai_limit=50` бюджетом:** это число выбранных единиц за один проход, не batch отправки модели и не ограничитель стоимости между запусками. Автоматический проход использует `ai_limit=None`, то есть весь накопившийся backlog, и не отсекается 50 единицами. `ai_limit` может остаться опциональной технической настройкой диагностики/нагрузки, но не продуктовой квотой.

В этой задаче основной предмет реализации — планирование и оркестрация. Полный учёт и бюджеты — **отдельные зависимые задачи ниже**, а не незаметно добавляемые в ITD-84 без оценки объёма.

### 4.1. Автоматический AI без контроллера расходов (решение 2026-10-29)

- При включённом расписании выполняется полный автоматический проход: сбор,
  нормализация, кластеризация, затем существующий общий AI-этап по всему backlog
  (`ai_limit=None`) и его штатная асинхронная постановка персональной оценки.
- Жёсткой денежной квоты нет: расходы автоматического прохода денежно не
  ограничены. Не маскировать это `ai_limit=50` или обещанием «при ошибке
  остановим»; отсутствие контроля — известное ограничение, а не защита.
- `SCHEDULED_PAID_AI_ENABLED=true` (по умолчанию) включает автоматический AI;
  `false` — только бесплатные стадии, без AI и постановки Relevance (причина
  `paid_ai_disabled`). Ручной явный AI-запуск сохраняет прежнее поведение.
- Учёт фактических расходов, глобальный бюджет, пользовательские квоты и
  отображение лимитов остаются отдельными задачами 4.4. Когда они будут готовы,
  проверка бюджета подключается к каждому платному вызову без изменения
  контрактов анализа, relevance и моделей.

### 4.2. Две независимые учётные модели

1. **Фактические расходы платформы:** один реальный платный вызов провайдера → одна запись реального расхода (в том числе реально тарифицированный неуспешный/не сохранённый вызов). Отдельно учитывать глобальную сумму, дневной лимит и доступный остаток кошелька/кредита провайдера; внутренний остаток сверять с внешним провайдером, не приравнивать к нему без проверки.
2. **Пользовательское виртуальное потребление:** пользователь получает одну версию единицы контента → один тарифный дебет за вычислительную услугу, **даже если Summary/Importance уже лежали в общем кэше**. Повторное чтение той же версии не дебетует снова. Персональная Jev Relevance добавляется к его потреблению, реальный вызов фиксируется отдельно.
3. **Аналитическая доля общих затрат:** отдельно от прямых персональных расходов и виртуальной тарифной стоимости сохраняется/рассчитывается доля фактических общих Summary/Importance, относимая к пользователю по зафиксированным правилам. Показывать метрики раздельно: `direct_actual`, `shared_allocated`, `virtual_consumption`. Сумма виртуальных дебетов многих пользователей **не должна** называться реальной суммой расходов платформы.

События связывать с `user_id`, `kind`/`unit_id`, версией/fingerprint результата, операцией, моделью и временем; поддерживать агрегацию за сутки/неделю/месяц, в том числе по тарифу. Цена виртуального потребления — единая прозрачная тарифная методика, не обязательно равная реальному кэширующему расходу. Версионировать тарифы и правила аллокации, чтобы история не пересчитывалась молча при смене подписчиков/цен. Для пользователя важен первый факт предоставления/выдачи результата (или однозначное фиксируемое включение в доступный ему набор); правило события списания нужно окончательно согласовать с API ленты и с лимитом доступа до релиза квот.

**Глобальный бюджет — жёсткий:** до каждого платного запроса атомарно резервировать **ограниченную максимальную** стоимость с учётом конкурирующих Worker; неизвестная цена/невозможность безопасной оценки → не отправлять запрос. После ответа сверять резерв с фактическим биллингом; провайдерские таймауты/неопределённые списания учитывать отдельным статусом и не освобождать их без проверки. Точный потолок невозможен без контроля max tokens/цен всех тарифицируемых составляющих и остатка внешнего кошелька.

**Пользовательский бюджет — мягкий:** ориентир **USD 1 на пользователя в день** (конфигурируемо, зависит от будущего тарифа). Если квота была доступна до начала единицы, дать текущей единице завершиться, даже при небольшом перерасходе, затем не начинать новые платные пользовательские операции/не предоставлять следующие платные единицы, пока квота не обновится. Глобальный жёсткий бюджет при этом **всегда имеет приоритет**; если недостаточно его резерва на очередной вызов, операцию не начинать. Остановку пользовательской выдачи и начисления за переиспользованные результаты обеспечивать даже при полном общем кэше.

Общие расходы нельзя приписывать одному пользователю как «деньги, которые он реально вызвал к расходу»: непосредственную персональную цену Relevance измеряем отдельно, долю общих расходов считаем по явному аналитическому правилу. После изменения числа получателей показывать сохранённые/версионированные данные, а не незаметно переписывать историю.

### 4.3. Единый будущий интерфейс учёта AI

Любой оплачиваемый шаг проходит через общий интерфейс budget check / reservation / usage record:
- `summary`: OpenRouter, сейчас есть `usage` и необязательный `cost_usd`;
- `importance`: Jev, токены уже читаются, денежный `cost_usd` ещё нужно корректно вычислять;
- `relevance`: Jev, текущая **персональная классификация** по интересам, токены уже читаются, стоимость пока не вычисляется;
- новые будущие AI-операции должны подключаться к этому интерфейсу без новой разрозненной системы квот. **Не** выдавать детерминированное извлечение сущностей за оплачиваемую классификацию.

Хранить отдельные журнал реальных вызовов, журнал тарифных дебетов пользователей и данные аллокации. Считать расходы за день/неделю/месяц по времени и версии модели/тарифа, учитывать кэш, повторный запуск, ошибки, пустой `usage`, дубли и повторные попытки. Для Jev подтвердить источник цены (провайдерский billing или проверенный тарифный каталог) до применения жёстких бюджетов.

### 4.4. Связанные задачи (выделить в отдельные тикеты/PR)

1. **AI Cost Metering:** общий журнал фактических AI-вызовов, токенов, моделей/провайдеров, биллинга, неизвестных и ошибочных списаний; расчёт денежной стоимости Jev Importance/Relevance; договор об ошибках/повторах, версия тарифа, тесты.
2. **Global Budget & Wallet:** жёсткие дневные/общие ограничения, атомарные резервы перед **каждым** платным запросом, сверка с внешним балансом, безопасная остановка, работа параллельных Worker и неизвестных цен.
3. **User Quotas & Virtual Accounting:** виртуальный дебет за общий и персональный результат (включая кэш), раздельные direct/shared/virtual метрики, USD 1/день как первичное предложение, повторная выдача без двойного списания, контроль доступа при превышении лимита, отчёты день/неделя/месяц и правила исторической аллокации.
4. **User-facing Quota & Subscriptions:** API и UI для остатка, использованного бюджета и причин остановки, описание лимитов в PR/документации продукта, тарифы и подписки. Не путать виртуальные кредиты пользователя с фактическим балансом провайдера.

**Статус зависимостей:** ранее планировалось включать unattended paid AI только
после пунктов 1 и 2; решением от 2026-10-29 это ограничение снято — полный
автоматический AI уже включён без них. Пункты 1–2 нужны для последующего контроля
и ограничения расходов, пункт 3 — до пользовательских планов и защиты от
безлимитного потребления кэша, пункт 4 — до публичного вывода коммерческих
лимитов. В ITD-84 эти подсистемы не внедрены.

## 6. Приёмочные сценарии

1. При запуске профиля Compose Beat периодически отправляет одну общую задачу; Worker выполняет её, результаты и логи доступны. Проверка планировщика — только реальный Beat: прямой вызов `run_shared_pipeline` или ручной CLI его не заменяет.
2. Два пользователя подписаны на одинаковый канал → канал опрашивается один раз за проход, но пользователям доступен общий результат по правилам доступа.
3. Все четыре типа источников проходят через существующий `sync_source`; сбой одного не теряет успехи остальных.
4. Нормализация, сущности, кластеризация и актуальные глобальные Summary/Importance выполняются в штатном порядке; общие операции не повторяются за каждого пользователя; персональная Relevance остаётся асинхронной.
5. Повторный запуск без новых публикаций не инициирует повторные платные вызовы по актуальным fingerprints.
6. Наложение двух расписаний и ручного запуска: одновременно только один глобальный проход; второй корректно пропускается. Проверить сценарии падения Worker и возврата lock.
7. При недоступном брокере/провайдере не теряются сохранённые публикации; ошибки видны, последующий проход повторяет незавершённую работу.
8. На расписании работает полный автоматический AI (по решению 2026-10-29, без контроллера расходов); `SCHEDULED_PAID_AI_ENABLED=false` оставляет только бесплатные стадии без AI и постановки relevance.
9. Когда денежный контроль готов, большое число публикаций не отсекается неявным `ai_limit=50`: прекращение/пауза по бюджету и возобновление на следующих проходах. Тест именно с реальными резервами, а не mock-проверкой суточной суммы один раз.
10. Для использования денежного контроля в тестах проверить границы жёсткого глобального и мягкого пользовательского лимитов, двойные Celery-попытки, кэш-повторную выдачу, unknown pricing и совпадение фактического ledger с платежами.
11. Проверить тестами и реально поднятыми Redis/PostgreSQL/Worker/Beat; не считать успешный `delay()` доказательством выполнения задачи. Определить граф зависимостей PR перед включением фоновых расходов.

## 7. Открытые решения

- Принять конкретный интервал обновления (предложение — 30 минут), возможные разные интервалы по типам источников и ограничения платформ.
- Требуется ли операционный предел времени одного запуска и распределение долгих стадий на независимые задачи; не смешивать с денежной квотой.
- Финальный момент дебета за общую публикацию: первая выдача, включение в ленту или персонально готовый результат; без такого события невозможен точный контроль кэшированных потреблений.
- Точная валюта/период окна лимита, источник сведений об остатке провайдера, политика аллокации общего расхода, тарификация и точность оценки до запроса.
- Как отображать пользователю частично готовые материалы, когда их сбор завершён, но AI ожидает бюджет; и какие этапы видимости ленты блокируются мягкой квотой.
- Когда появятся metering и бюджеты: момент проверки/резервирования и порог остановки автоматического прохода; сейчас автоматический AI работает без этих проверок по решению от 2026-10-29.

Пока эти вопросы не решены, не выдавать технический лимит публикаций за финансовый предохранитель. Автоматические платные задачи сейчас включены осознанно (см. 4.1): контроля расходов нет, и это известное ограничение, а не гарантия остановки.

## 8. Состояние реализации

Реализовано в этом изменении:

- `app/pipeline/run.py`: общая оркестрация глобальных стадий. `run_shared_pipeline`
  (`sync_active_sources` ровно один раз → нормализация → извлечение сущностей →
  кластеризация с commit → существующий `run_common_analysis` с `ai_limit=None` и
  его штатная постановка relevance) и ручной `run_pipeline` используют одну
  реализацию стадий; CLI, `--dry-run`, `--fixture` и текущие гарантии отсутствия
  платных вызовов сохранены. `allow_paid_ai=True` по умолчанию; `False` — только
  бесплатные стадии, без AI и постановки Relevance. Результат прохода содержит
  статусы источников и суммарные
  счётчики публикаций (`fetched`/`saved`/`inserted`/`updated`), а
  `normalize.failed > 0` или ошибки AI дают статус `completed_with_failures`.
- `app/pipeline/lock.py`: сессионный `pg_try_advisory_lock` PostgreSQL с
  фиксированным пространством имён на выделенном соединении `AUTOCOMMIT`.
  Блокировка общая для ручного реального и автоматического запусков, снимается в
  `finally`, соединение выводится из пула; занятость даёт `skipped_locked`,
  потеря блокировки (`PipelineLockLost`) прерывает проход без повторного захвата.
  Watchdog проверяет владение по таймеру, пока ожидается асинхронная стадия.
  Гарантия — координация через общий PostgreSQL, не распределённый fencing:
  блокирующий синхронный сбор источников не прерывается, поэтому после потери
  могут завершиться несколько текущих вызовов источников, а сетевой разрыв не
  отменяет уже начатый внешний HTTP-вызов.
- `app/workers/tasks.py` / `app/workers/celery_app.py`: задача
  `pipeline.run_scheduled` (`asyncio.run`, компактный JSON) и расписание Beat из
  `SCHEDULED_PIPELINE_ENABLED` / `SCHEDULED_PIPELINE_INTERVAL_SECONDS` (UTC,
  по умолчанию 1800 секунд, расписание пустое при выключенном флаге) и
  `SCHEDULED_PAID_AI_ENABLED` (по умолчанию `true`). Задачи `relevance.*`
  сохранены.
- `app/core/config.py`, `.env.example`, `docker-compose.yml`, `docs/DEVELOPMENT.md`,
  `docs/ARCHITECTURE.md`: настройки (включая необязательный
  `SCHEDULED_PIPELINE_SOURCE_LIMIT` — лимит на источник, не бюджет), один Beat,
  готовность PostgreSQL/Redis и миграций, перезапуск, логи и ограничения.
- Проверка advisory lock: unit-тесты на stub плюс env-gated
  `tests/test_pipeline_lock_postgres.py` на одноразовом PostgreSQL. Он закрывает
  реальный контракт SQLAlchemy 2.0, из-за которого ломался живой запуск:
  `execution_options(isolation_level=...)` после `detach()` падает
  (`AttributeError: finalize_callback`); правильный порядок —
  `execution_options` → `detach` → lock, а сбой до detach инвалидирует и
  физически закрывает соединение.
- Транзакционные исправления, обнаруженные при реализации: YouTube-коннектор
  читает кэш расшифровок в короткой сессии и выполняет HTTP вне пишущей
  транзакции; `HabrService.sync_publications` коммитит источник до сети,
  завершает читающую транзакцию до загрузки полных текстов и коммитит каждую
  страницу. Reddit и Telegram уже использовали короткие транзакции.

Автоматический AI: по решению от 2026-10-29 полный автоматический проход
включает Summary/Importance и постановку персональной Relevance без контроллера
расходов; жёсткой денежной квоты нет, `ai_limit` остаётся техническим пределом, а
не бюджетом. Автоматический проход использует `ai_limit=None` — весь backlog.
`SCHEDULED_PAID_AI_ENABLED=false` — только бесплатные стадии, без AI и
постановки Relevance (причина `paid_ai_disabled`). Ручной явный AI-запуск
сохраняет прежнее поведение, включая свой `--ai-limit`.

Остающиеся зависимости (не входят в ITD-84, будущая работа): «AI Cost Metering»,
«Global Budget & Wallet», «User Quotas & Virtual Accounting», «User-facing Quota &
Subscriptions». Это контроль и отображение расходов, а не блокирующее условие для
текущего автоматического прохода. Уже развёрнутые runtime `.env` не меняются:
полный auto AI включается явным `SCHEDULED_PIPELINE_ENABLED=true` (и `true` в
`SCHEDULED_PAID_AI_ENABLED`) с перезапуском worker/beat.
