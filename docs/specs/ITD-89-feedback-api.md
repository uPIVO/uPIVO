# ITD-89 — API обратной связи по публикациям и инфоповодам

**Статус:** спецификация для реализации; исполняемый код не изменён.  
**Задача:** [ITD-89 в YouGile](https://yzcjhacj.yougile.com/team/74c58e471796/#ITD-89).  
**База спецификации:** `feat/ITD-86-user-interests` (PR #13).  
**Связанные работы:** ITD-86 (интересы и персональная оценка), ITD-17 (общая единица анализа), ITD-85 (оркестрация), лента и дайджест.

## 1. Цель и границы

Пользователь может оценить **отображаемую единицу контента** как `useful` («полезно») или `not_interested` («неинтересно»), изменить реакцию, убрать её и получить свои текущие реакции. Сервер хранит **одну текущую реакцию** на пару «пользователь + единица» в PostgreSQL. Реакции доступны для последующих алгоритмов персонализации, но **не влияют на ранжирование, интересы или AI-оценку в рамках ITD-89**.

Единица контента — ровно одно из:
- `feed_item`: отдельная публикация `feed_items`, **не состоящая в кластере**;
- `cluster`: целый инфоповод `content_clusters`, карточка которого агрегирует одну или несколько публикаций. Оценка кластера **не создаёт реакций на его участников**.

Отдельные singleton-кластеры ради реакций не создавать. В одной выдаче нельзя показывать и оценивать одновременно кластер и его участников как самостоятельные карточки. Не копировать публикации в персональные таблицы.

**Не входит:** интерфейс, авторизация/JWT, история действий или оценок, `open_full` и другие неявные события, статистика/аналитика, новые параметры LLM, автоматическая корректировка `user_interests` или `user_item_scores`, пересчёт рангов и фоновые задачи. Нельзя подменять этим API существующую AI-оценку `relevance_score`.

## 2. Контекст существующего кода

- FastAPI с префиксом `/api`, синхронные SQLAlchemy `Session` через `get_db`, явные commit/rollback и Alembic.
- `backend/app/api/interests.py`, `backend/app/api/users.py` — примеры пользовательских HTTP-маршрутов. До внедрения настоящей авторизации идентификатор пользователя — `users.id` в URL. **Это не проверка личности**.
- `backend/app/models/content_cluster.py`: `ContentCluster` и `ClusterItem`; отдельная публикация может стать участником кластера.
- `backend/app/models/user_item_score.py` уже поддерживает взаимоисключающие `feed_item_id` и `cluster_id` с отдельными UNIQUE. **Реакции — отдельная таблица, не столбец `user_item_scores`.**
- `backend/app/services/feed.py` уже создаёт одну карточку для кластера и карточку для одиночной публикации на основе включённых `user_sources`; выдаёт `cluster_id` и `is_cluster`.
- `docs/user-interests.md`: для кластера достаточно одного участника из включённого источника; механизма фактически просмотренных/показанных карточек **пока нет**.
- В Gramax уже концептуально определены `feedback` и значения `useful` / `not_interested`, но первоначальная схема ориентирована только на `feed_item_id`. ITD-89 расширяет контракт до двух типов единиц.

**Зависимость:** выполнять миграцию после имеющегося на базовой ветке `0011_user_interests`. Не изменять существующие миграции; при интеграции с другими ветками проверить актуальную цепочку Alembic.

## 3. Что разрешено оценивать

Пользователь оценивает **целую карточку, которую ему может вернуть действующая пользовательская выдача** (лента/дайджест), а не произвольную запись из общей БД.

Правила для **первой установки** и **смены** реакции:
1. Пользователь существует.
2. `kind=feed_item`: запись существует, не входит в `cluster_items`, принадлежит источнику с включённым `user_sources(user_id, source_id, enabled=true)` и имеет допустимый для текущей ленты статус обработки (`normalized` или `processed`).
3. `kind=cluster`: кластер существует; хотя бы один его участник удовлетворяет тому же правилу включённого источника и статуса. Не требуется, чтобы **все** участники кластера были из подписок пользователя: единая сводка инфоповода может включать и другие источники.
4. Нельзя поставить индивидуальную оценку участнику кластера через `kind=feed_item`, даже если он виден на экране деталей кластера. Клиент использует `kind=cluster`, `unit_id=cluster_id`.
5. Если материал удалён или сейчас недоступен по правилам показа, установка/смена возвращает **404**, не раскрывая наличие контента другого пользователя.

**Важное ограничение текущей реализации:** проверка включённых источников и состояния контента устанавливает *возможность показа*, а **не факт показа конкретной карточки на экране**. В ITD-86 нет таблицы показов и адаптера `ViewedStatusProvider`. Поэтому нельзя утверждать, что бэкенд уже способен доказать «этот пользователь увидел эту карточку». В ITD-89 использовать общий предикат доступности из ленты (вынести/переиспользовать, чтобы правила не расходились); не создавать фиктивный учёт просмотров и не считать ответ API фактом просмотра. Если впоследствии требуется строго «только фактически показанные», понадобится отдельный механизм событий показа и уточнение контракта.

Ранее записанная реакция **не удаляется автоматически** при отключении источника; её можно прочитать и удалить в рамках своего `user_id`. Новое `PUT` для ставшей недоступной карточки не допускается. При изменении группировки реакция остаётся привязанной к исходному типу и ID, **не переносится** автоматически между `feed_item` и `cluster` и не подставляется в новую карточку другого типа. Удаление самой единицы удаляет зависимую реакцию по FK.

## 4. HTTP-контракт

Все маршруты ниже начинаются с `/api`. Для обратной связи выбран **идемпотентный PUT**: он позволяет одной операцией поставить или заменить текущую оценку; отдельные POST и PATCH для одной и той же операции не нужны.

| Метод | Путь | Действие | Успех |
| --- | --- | --- | --- |
| `PUT` | `/users/{user_id}/feedback/{kind}/{unit_id}` | Создать / изменить оценку | `201` (новая), `200` (имеющаяся) |
| `GET` | `/users/{user_id}/feedback/{kind}/{unit_id}` | Получить текущую реакцию | `200` |
| `DELETE` | `/users/{user_id}/feedback/{kind}/{unit_id}` | Снять оценку | `204` |
| `GET` | `/users/{user_id}/feedback` | Получить реакции пользователя | `200`, включая `[]` |

`kind`: только `feed_item` или `cluster`; `user_id` и `unit_id`: целые положительные идентификаторы. **ID разных таблиц могут совпадать; тип обязателен.** Не использовать `is_cluster` или `feed_items.id` главной публикации как замену `cluster_id`.

### PUT /users/{user_id}/feedback/{kind}/{unit_id}

Тело:

```json
{"reaction": "useful"}
```

Допустимое другое значение: `"not_interested"`. Нет нейтральной третьей реакции: «без оценки» реализуется удалением.

- Если записи нет, вставить и вернуть `201 Created`.
- Если была другая реакция, **перезаписать её в той же строке** и вернуть `200 OK`, обновив `updated_at`.
- Если реакция совпадает, вернуть `200 OK`, **не изменяя** `updated_at`. Повторный запрос не создаёт дубликат.
- Неизвестные поля и неверные значения отклонять как `422` (строгая Pydantic-схема).
- Конкурентные запросы не должны нарушать UNIQUE или приводить к необработанной ошибке. При одновременной установке разных значений допустима семантика последней успешно зафиксированной операции; гарантировать атомарность каждой записи, а не порядок прихода запросов.

Пример ответа для кластера:

```json
{
  "id": 91,
  "user_id": 12,
  "kind": "cluster",
  "unit_id": 34,
  "reaction": "useful",
  "created_at": "2026-10-28T10:00:00",
  "updated_at": null
}
```

Для одиночной публикации ответ имеет `kind=feed_item` и `unit_id=feed_items.id`. Не включать чужие данные, исходные публикации, AI-score или историю в ответ.

### GET /users/{user_id}/feedback/{kind}/{unit_id}

Возвращает одну принадлежащую пользователю запись в том же формате, что PUT. Отсутствие реакции — `404`, в том числе для чужого `user_id`/записи. Это **не означает**, что публикации нет: отсутствие реакции — нормальное состояние. Чтение существующей реакции допускается и после отключения источника.

### GET /users/{user_id}/feedback

По умолчанию возвращает массив текущих реакций `[]` или объекты того же формата, в порядке `created_at DESC, id DESC`. Параметры:
- `limit` (1–100, по умолчанию 20), `offset` (неотрицательное, по умолчанию 0);
- необязательный `kind` для отбора `feed_item` или `cluster`.
- для подгрузки оценок **конкретных видимых карточек**: допускается повторяемый параметр `unit_id` (от 1 до 100 значений) **только вместе с `kind`**. В этом режиме вернуть текущие реакции на запрошенные ID одним запросом к БД, без пагинации; единицы без реакции просто отсутствуют в массиве. Повторные ID дедуплицировать.

Параметры фильтрации относятся к **ID соответствующей таблицы**, а не к числовому ID другой сущности. Нет необходимости выдавать все реакции всех пользователей или выполнять по одному DB-запросу на карточку.

### DELETE /users/{user_id}/feedback/{kind}/{unit_id}

Физически удалить **только** соответствующую строку `feedback`, не изменять `feed_items`, `content_clusters`, `user_item_scores` или данные других пользователей. Повторное удаление — `204 No Content`; если пользователя нет — `404`. Удалять собственную текущую реакцию можно независимо от активности источника.

## 5. Ошибки

| Ситуация | Код |
| --- | --- |
| Пользователь не существует | `404` |
| Нет текущей реакции на GET конкретной единицы | `404` |
| PUT для отсутствующей / недоступной / уже вошедшей в кластер одиночной публикации | `404` |
| Недопустимый `kind`, `unit_id`, `user_id`, `reaction`, пустой JSON, лишние поля | `422` |
| Нет реакций в общем GET | `200` + `[]` |
| Повторный PUT той же реакции | `200`, запись не меняется |
| Повторный DELETE | `204` |
| Ошибка PostgreSQL | штатная серверная ошибка, `rollback`, логирование без SQL/секретов в ответе |

Валидацию проводить до записи. Исключить утечку сведений о недоступных чужих материалах через различающиеся сообщения ошибок.

## 6. PostgreSQL и Alembic

Ввести ORM `Feedback` и новую миграцию от `0011_user_interests` (ориентир имени: `0012_feedback`; перед реализацией сверить актуальный head). **Не переписывать прежние миграции.**

Таблица `feedback`:

| Поле | Тип | Ограничения |
| --- | --- | --- |
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | PK |
| `user_id` | `BIGINT` | NOT NULL, FK `users.id ON DELETE CASCADE` |
| `feed_item_id` | `BIGINT` | NULL, FK `feed_items.id ON DELETE CASCADE` |
| `cluster_id` | `BIGINT` | NULL, FK `content_clusters.id ON DELETE CASCADE` |
| `reaction` | PostgreSQL enum `feedback_type` | NOT NULL; строго `useful`, `not_interested` |
| `created_at` | `TIMESTAMP WITHOUT TIME ZONE` | NOT NULL, DEFAULT CURRENT_TIMESTAMP |
| `updated_at` | `TIMESTAMP WITHOUT TIME ZONE` | NULL; только при фактической смене реакции |

Ограничения БД:
- `CHECK`: **ровно одно** из `feed_item_id` / `cluster_id` не NULL (XOR);
- `UNIQUE(user_id, feed_item_id)`;
- `UNIQUE(user_id, cluster_id)`;
- индекс для списка реакций пользователя `(user_id, created_at DESC, id DESC)`; при необходимости отдельно проверить индексы для каскадной очистки по FK.

Никаких таблиц `feedback_history`, записей старых/удалённых значений, soft-delete, `deleted_at` или отдельного журнала реакций. `created_at` и `updated_at` описывают **текущее состояние**, но не историю. Данные сохраняются в PostgreSQL; не дублировать их в `raw_payload` или Redis.

Использовать атомарную вставку/обновление с разрешением конфликтов по соответствующему уникальному ключу либо транзакционный эквивалент, безопасный для одновременных запросов. Не выполнять внешние HTTP/LLM-вызовы внутри транзакции. Все изменения только по `user_id + kind + unit_id`.

## 7. Контракт для будущей персонализации

Сервис должен предоставлять способ получить текущую реакцию или набор реакций по парам `(kind, unit_id)` конкретного пользователя без N+1. Зафиксированные значения:
- `useful`: явный положительный сигнал;
- `not_interested`: явный отрицательный сигнал;
- запись отсутствует: **сигнала нет**, а не отрицательная реакция.

**Не задавать сейчас вес реакции**, не менять `rank_score`, `relevance_score`, не редактировать `user_interests`, не пересчитывать `user_item_scores`, не генерировать задачи Celery. Это самостоятельный следующий этап. Сохранение/изменение/удаление должно быть быстро выполнимо синхронно через БД.

Если `feed_item` позднее становится членом кластера, его ранее сохранённая текущая реакция **не является реакцией на новый кластер**. Она не должна попадать в реакцию карточки кластера. Не переносить и не объединять оценки автоматически: политика миграции сигнала при перегруппировке относится к будущей персонализации, и не может вводиться неявно.

## 9. Критерии приёмки

1. `PUT` новой реакции допустимой одиночной публикации даёт `201`; повторный PUT — `200` без изменения `updated_at`.
2. Изменение `useful` ↔ `not_interested` даёт `200`, обновляет ту же строку; прежнее значение и история нигде не сохраняются.
3. `DELETE` даёт `204` и физически удаляет реакцию; повторный DELETE также `204`. Нет нейтральной третьей реакции.
4. Два пользователя независимо оценивают один `feed_item` или `cluster`, чужих записей API не возвращает и не меняет.
5. Один пользователь может иметь независимые реакции на `feed_item(id=N)` и `cluster(id=N)`; смешения ID не происходит.
6. Включённый источник позволяет оценивать отдельную карточку из него; источник, не подключённый или выключенный, не позволяет ставить новую реакцию (`404`).
7. Кластер можно оценить, если хотя бы один видимый участник из включённого источника; не требуется подписка на все источники кластера.
8. Участника кластера нельзя отдельно оценить как `feed_item`; оценка кластера не добавляет оценки участникам.
9. Чтение/удаление своей прежней реакции после отключения источника работает; поставить новую/изменить реакцию на недоступную единицу нельзя.
10. `GET` списка и групповой запрос по ID возвращают только существующие текущие реакции нужного пользователя, без N+1, с корректными фильтрами и пагинацией.
11. PostgreSQL CHECK/FK/UNIQUE и конкурентные PUT проверены **на настоящей тестовой PostgreSQL**, включая каскадное удаление и несовпадающие типы целей.
12. Корректно обрабатываются 404/422, откат транзакций и несуществующие ID. OpenAPI содержит все операции; применяются и откатываются миграции на **одноразовой** БД.
13. Реакции не меняют интересы, AI-оценки, ранги, выдачу, содержимое публикаций/кластеров и не запускают фоновые работы.
14. Не реализована фиктивная «просмотренность»: тесты подтверждают ограничение по доступности текущей ленты, но не утверждают фактического показа на экране.

## 10. Дополнительные замечания при интеграции

- Источник истины для выбора *единицы* — лента/дайджест: `cluster_id` для общей карточки или `feed_items.id` для одиночной. На момент написания `FeedService` уже группирует кластеры, но учёт фактических показов ещё не реализован.
- Ветка ITD-86 также определяет `ViewedStatusProvider`, который пока возвращает неизвестный статус без адаптера; **не подменять** его записью реакции.
- Концептуальную DBML-модель `feedback` в Gramax при отдельном поручении потребуется синхронизировать с новым `cluster_id` и XOR; в рамках этой спецификации не изменять чужой репозиторий документации.
- При интеграции убедиться, что другие фичи не ввели свои таблицы реакций/миграцию с тем же номером. Не смешивать явную обратную связь с неявным событием `open_full`.

## 11. Проверки после реализации

Из `backend/`: запустить `uv run pytest` и `uv run ruff check .`; отдельно — интеграционные PostgreSQL-тесты для уникальности, CHECK, FK/CASCADE, конкуренции, миграций и проверок источников. Документ спецификации не является подтверждением прохождения этих проверок.
