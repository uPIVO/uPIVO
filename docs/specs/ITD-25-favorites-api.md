# ITD-25 — API «Избранное»

Статус: спецификация для реализации (без изменений исполняемого кода).
Задача: [ITD-25 в YouGile](https://yzcjhacj.yougile.com/team/74c58e471796/#ITD-25).
Базовая ветка: main.

## 1. Назначение и границы

Пользователь может сохранить доступную ему публикацию в личное избранное, просмотреть список сохранённого, изменить личную заметку и убрать материал из избранного.

Обязательные операции:
1. Добавить существующий FeedItem в избранное.
2. Получить список избранного пользователя.
3. Обновить заметку к сохранённому материалу.
4. Удалить материал из избранного.

Используется **общий FeedItem** в PostgreSQL; персональные данные лежат в отдельной таблице favorites. Не копировать публикации и не создавать пользовательские дубликаты FeedItem.

В объём ITD-25 не входят: регистрация/авторизация, JWT, OAuth, папки, поиск по сохранённому, самостоятельное создание публикаций, лента/дайджест, настройка персонализации. Сохранение может позже стать сигналом ранжирования, но применение такого сигнала — отдельная задача.

## 2. Существующий контекст (main)

- FastAPI: текущие HTTP-маршруты подключаются в backend/app/main.py с префиксом /api; в качестве примера — backend/app/api/habr.py.
- SQLAlchemy 2, синхронная Session через get_db; транзакции записи завершаются явным commit / rollback.
- Таблицы users, sources, user_sources и feed_items уже существуют в миграциях и ORM.
- FeedItem глобален, а UserSource — связь пользователя с источником; UserSource.enabled определяет, подключён ли источник.
- Авторизация отсутствует. В имеющемся CLI сбора пользователь выбирается явно по ID или email; в пользовательском HTTP API пока нет сложившегося способа определения текущего пользователя.
- Полноценный пользовательский Feed/Digest HTTP API пока не реализован.
- В проектной DBML и Gramax-модели уже предусмотрена favorites: id, user_id, feed_item_id, note, created_at, UNIQUE(user_id, feed_item_id). Эта таблица пока **не введена действующей миграцией**.

См. docs/ARCHITECTURE.md, docs/DEVELOPMENT.md, backend/app/models/{feed_item,user,user_source}.py и репозиторий проектной документации ItzEnden/uPIVO_Gramax (04-system-requirements.md, 08-database-model.md, 09-database-schema.md).

## 3. Пользовательский контекст и доступность

**Решение для текущего этапа:** user_id явно передаётся как положительный целочисленный параметр пути /api/users/{user_id}/favorites. Это идентификатор пользователя для привязки данных, **не доказательство его личности и не механизм авторизации**. Не внедрять JWT, фиктивную сессию или иные auth-компоненты внутри ITD-25.

При появлении настоящей авторизации сервер обязан получать идентификатор из проверенной сессии/токена; нельзя продолжать доверять произвольному user_id клиента. До этого API является только интерфейсом разработки и **не должен публиковаться как безопасный многопользовательский сервис**.

Требование «сохранять только те публикации, которые пользователь видит»:
- При первом добавлении публикация должна существовать и быть доступной этому пользователю.
- Пока нет персонального Feed API, проверяем минимально реализуемое правило: существует включённая связь user_sources для указанного user_id с source_id сохраняемого feed_items (user_sources.enabled = true).
- Запрещено использовать существование записи в глобальной feed_items как единственное разрешение на сохранение.
- Когда появится единое правило видимости ленты/дайджеста (включая источники, рекомендованный контент, права и фильтрацию), проверку сохранения нужно **переиспользовать из него**, а не держать независимые, расходящиеся правила.
- Временная проверка по подключённым источникам определяет доступность контента, но сама по себе **не доказывает, что конкретная карточка была показана на экране**. Учёт реально показанных публикаций сюда не входит.

После успешного сохранения запись принадлежит пользователю. Отключение источника в дальнейшем не удаляет уже сохранённое: оно продолжает отображаться в избранном и доступно для изменения заметки/удаления; новые сохранения из отключённого источника запрещены. Повторное добавление уже сохранённого материала не создаёт дубль и не изменяет note.

Каждая операция чтения, изменения и удаления изолирована условием user_id **и** идентификатором публикации; один пользователь не видит заметки и сохранения другого. До внедрения auth это логическая изоляция данных по указанному ID, но не полноценная защита от выдачи себя за другого пользователя.

## 4. HTTP API

Все пути ниже начинаются с /api. ID пользователя и публикации — положительные bigint, валидируемые на уровне FastAPI.

| Метод | Путь | Назначение | Успех |
| --- | --- | --- | --- |
| POST | /users/{user_id}/favorites | Добавить FeedItem, при желании сразу с note | 201 Created; 200 OK, если уже сохранён |
| GET | /users/{user_id}/favorites | Список сохранённых материалов | 200 OK |
| PATCH | /users/{user_id}/favorites/{feed_item_id} | Частично изменить запись избранного (сейчас только note) | 200 OK |
| DELETE | /users/{user_id}/favorites/{feed_item_id} | Удалить запись избранного | 204 No Content |

В URL конкретной записи используется **feed_item_id**, а не favorites.id: клиент уже знает ID публикации из ленты и может сохранить/убрать её без дополнительного поиска идентификатора связи. В ответах favorites.id остаётся доступным как технический идентификатор записи.

### POST /api/users/{user_id}/favorites

JSON-запрос:

~~~json
{
  "feed_item_id": 42,
  "note": "Проверить инструмент в проекте"
}
~~~

- feed_item_id обязателен, note опционален, по умолчанию null.
- note допускает строку или null; пустая строка допустима, null означает отсутствие заметки.
- Если пользователя нет — 404.
- Если FeedItem отсутствует или не доступен пользователю по правилу раздела 3 — 404 с общей ошибкой, без раскрытия чужого контента.
- Если запись новая — создать связь и вернуть 201 с объектом избранного.
- Если пара user_id + feed_item_id уже сохранена — вернуть существующий объект с 200, **не перезаписывать существующую заметку**, даже если в запросе была иная note.
- Конкурентные POST не создают дублей: уникальность обеспечивается БД; использовать conflict-safe insert или обработку конфликта с повторным чтением.

Пример успешного ответа (такой же формат записи в GET и PATCH):

~~~json
{
  "id": 87,
  "user_id": 12,
  "feed_item_id": 42,
  "note": "Проверить инструмент в проекте",
  "created_at": "2026-10-24T08:00:00",
  "feed_item": {
    "id": 42,
    "source_id": 3,
    "source_name": "Habr",
    "title": "Обзор инструмента",
    "summary": null,
    "original_url": "https://example.com/article",
    "author": null,
    "published_at": null
  }
}
~~~

Свойства записи из feed_items — только для чтения. source_name берётся из sources. timestamp-формат соответствует текущим моделям БД (timestamp without time zone); не вводить в этой задаче несогласованное изменение временной модели.

### GET /api/users/{user_id}/favorites?limit=20&offset=0

- limit: целое 1..100, по умолчанию 20; offset: целое >= 0, по умолчанию 0. Как и в текущем GET /api/habr/saved.
- Возвращает JSON-массив объектов описанного выше формата; при отсутствии записей — [].
- Сортировка: сначала самые недавно сохранённые, по (favorites.created_at DESC, favorites.id DESC) для однозначного порядка.
- Отбираются только записи favorites.user_id = user_id; note и данные FeedItem отдавать одним запросом с необходимыми JOIN (без N+1).
- Применять пагинацию к записям избранного до сериализации.
- Для неизвестного user_id — 404. Никаких данных других пользователей в ответе.

### PATCH /api/users/{user_id}/favorites/{feed_item_id}

JSON-запрос:

~~~json
{"note": "Обновлённая заметка"}
~~~

- Сейчас единственное изменяемое поле — note; отдельный /note endpoint не требуется.
- PATCH — частичное обновление **записи favorites**, а не FeedItem. Ни title, ни summary, ни содержимое публикации этим API изменять нельзя.
- Переданную строку записать вместо старого значения. {"note": null} удаляет заметку. Пустой объект или запрос без note — 422.
- Неизвестные поля отклонять с 422, а не молча игнорировать.
- Не менять favorites.created_at при редактировании note; дополнительное updated_at не требуется текущей схемой.
- Если указанному пользователю запись не принадлежит или её нет — 404.
- Изменение заметки допускается и после отключения источника.

Если впоследствии появятся другие **свойства записи favorites**, их можно добавлять в тот же PATCH. Операции над папками или самим FeedItem нельзя автоматически включать в этот endpoint.

### DELETE /api/users/{user_id}/favorites/{feed_item_id}

- Удаляет **только** связку favorites, а не исходный глобальный FeedItem.
- При удалении существующей или уже отсутствующей записи возвращает 204 (идемпотентное поведение); пользователь должен существовать, иначе 404.
- Не затрагивает сохранения других пользователей.
- Может удалять запись независимо от текущего enabled соответствующего источника.

## 5. Ошибки и валидация

| Условие | HTTP |
| --- | --- |
| Неизвестный user_id | 404 |
| Несуществующий или недоступный FeedItem при новом POST | 404 |
| Нет записи favorites для указанного user_id при PATCH | 404 |
| Необработанные поля, пустой PATCH, неверные типы, некорректные ID/limit/offset | 422 |
| Некорректные данные POST (нет feed_item_id, неверный тип note) | 422 |
| Нет записей в GET | 200 + [] |
| Повторное добавление того же FeedItem | 200, исходная заметка сохраняется |
| Повторное удаление | 204 |
| Недоступна PostgreSQL или ошибка транзакции | штатная серверная ошибка без раскрытия SQL/секретов, rollback и logging |

Ошибки не должны включать содержимое чужих заметок или сырые DB-сообщения.

## 6. PostgreSQL / миграция

Новая ORM-модель Favorite и новая Alembic migration (не править уже применённые):

| Поле | Тип | Правило |
| --- | --- | --- |
| id | BIGINT GENERATED ALWAYS AS IDENTITY | PK |
| user_id | BIGINT | NOT NULL; FK -> users.id |
| feed_item_id | BIGINT | NOT NULL; FK -> feed_items.id |
| note | TEXT | NULL |
| created_at | TIMESTAMP | NOT NULL DEFAULT CURRENT_TIMESTAMP |

Обязательный UNIQUE(user_id, feed_item_id). Для сортировки/выборки конкретного пользователя — индекс по (user_id, created_at DESC, id DESC), если этого не покрывает выбранный план запроса. Отдельный индекс feed_item_id может понадобиться для операций по внешнему ключу и очистки; проверить по плану SQL и принятым соглашениям проекта.

Уникальность должна предотвращать гонку двух сохранений. Если в будущем появится удаление users/feed_items, политика зависимых favorites и ON DELETE должны быть согласованы с общим retention/cleanup проекта; в этой задаче не менять глобальные правила удаления.

PostgreSQL — единственный постоянный источник истины; не хранить favorites в Redis, файле, памяти процесса, raw_payload или внутри feed_items.

## 7. Размещение реализации

Предпочтительная структура в существующих слоях:

- backend/app/models/favorite.py — Favorite, ограничения, индексы;
- backend/app/models/__init__.py — регистрация модели для Alembic;
- backend/alembic/versions/... — новая последовательная миграция;
- backend/app/schemas/favorites.py — Pydantic-схемы запроса/ответа;
- backend/app/services/favorites.py — проверка доступа, выборки и изменения;
- backend/app/api/favorites.py — HTTP endpoint, валидация, Depends(get_db);
- backend/app/main.py — include_router(..., prefix="/api");
- backend/tests/test_favorites.py — unit/API тесты и интеграционная проверка с PostgreSQL.

Переиспользовать текущие SQLAlchemy Session, стиль FastAPI и error handling. Сервис не должен делать сетевой collection или запускать LLM при сохранении/чтении избранного. После изменений пройти ruff, pytest и проверку Alembic upgrade/downgrade на тестовой PostgreSQL.

## 8. Критерии приёмки

1. Есть миграция и ORM favorites; индексы и UNIQUE работают в PostgreSQL.
2. Пользователь с активным user_sources сохраняет существующий FeedItem и получает 201; общая публикация не дублируется.
3. Материал из неподключённого/отключённого источника впервые сохранить нельзя (404), даже если он есть в глобальной feed_items.
4. Пользователь A и пользователь B могут сохранить один FeedItem независимо, с разными заметками.
5. GET отдаёт только избранное указанного пользователя в порядке сохранения; limit/offset работают и предсказуемо сортируются.
6. PATCH меняет только note нужной записи; null очищает note; посторонние поля и пустой PATCH дают 422.
7. После отключения источника ранее сохранённая запись остаётся в избранном, её заметку можно менять, запись можно удалить.
8. DELETE убирает только пользовательскую связь, не удаляет FeedItem и не меняет чужое избранное; повторный DELETE = 204.
9. Повторный и параллельный POST не создаёт дублей и не затирает заметку.
10. Неверные ID, отсутствующие user/FeedItem, ошибки БД покрыты тестами; не раскрываются чужие данные.
11. OpenAPI /docs содержит все четыре операции; используется существующая схема запуска и транзакций.
12. Изменение не добавляет авторизацию и не изменяет другие функции сбора, обработки и отображения публикаций.

## 9. Отложенные зависимости

- **Авторизация:** будущий переход от user_id в URL к проверенной личности; до этого текущий API нельзя считать защищённым.
- **Персональная лента:** после появления общего определения «доступен/виден пользователю» заменить временную проверку по enabled user_sources на единый предикат с лентой/дайджестом. При необходимости усиления семантики до «фактически показан» нужна отдельная модель показов.
- **Папки/поиск:** уже присутствуют в более широких продуктовых требованиях, но не в формулировке ITD-25; разрабатывать отдельными задачами.

Не подменять эти будущие решения скрытым расширением текущей реализации.
