# ITD-85 — Завершение единого конвейера обработки публикаций

Статус: согласованная спецификация для реализации, **код не изменён**.  
Основание: запрос ITD-85 и исследование `main` репозитория 29.10.2026.

## 1. Цель и принятые решения

Подключить автоматический **общий** AI-анализ к существующему конвейеру после сохранения нормализации, извлечения сущностей и кластеризации. Не заменять существующие реализации сбора, нормализации, извлечения сущностей, кластеризации и ручного AI-анализа.

Решения владельца:
- Запуск обрабатывает **все требующие общего анализа единицы контента в общей БД**, а не только источники пользователя, указанного через `--user`. `--user` продолжает задавать область **сбора**.
- В рамках ITD-85 при запуске конвейера инициируются **`summary`, затем `importance`, затем фоновая `relevance`**. Общие операции выполняются один раз для единицы; персональная оценка ставится в Celery только для пользователей с включёнными источниками этой единицы и непустыми интересами (ITD-86).
- После успешного актуального общего AI-анализа `feed_items.processing_status` переводится в `processed`. Для кластера это относится к его участникам: у `content_clusters` отдельной колонки статуса нет.
- Использовать существующий `ContentUnitAnalysisUseCase` и контракты хранения, включая проверки устаревших данных.
- **База для разработки:** `feat/ITD-86-user-interests` (PR #13, ещё не в `main`); **не** ITD-89, поскольку обратная связь пользователей не требуется ITD-85. Стек PR: ITD-86 → ITD-85. При слиянии ITD-86 в `main` переподключить базу PR ITD-85.

## 3. Новый путь выполнения

~~~text
collect_for_user(--user)              [только подключённые источники пользователя]
          ↓
normalize_pending                     [общая БД]
          ↓
_extract_entities                     [общая БД]
          ↓
cluster_feed                          [общая БД]
          ↓ COMMIT — граница транзакции
select global analysis units          [общая БД]
          ↓
for each (kind, unit_id):
   ContentUnitAnalysisUseCase.run(operation="summary")
          ↓ только если summary актуальна
   ContentUnitAnalysisUseCase.run(operation="importance")
          ↓ только если обе операции актуальны и единица не изменилась
   mark participating FeedItem as processed  [успех общих операций]
          ↓
   enqueue relevance.score_content_unit_for_eligible_users(kind, unit_id)
          ↓
   Celery worker → eligible user(s) → relevance → user_item_scores
          ↓
aggregate common-AI and queueing statistics, report partial failures

[Результаты фоновой relevance могут появиться позже завершения конвейера]
~~~

### 3.1. Формирование единиц анализа

Выбирать из **текущего зафиксированного** состояния `feed_items` / `content_clusters` / `cluster_items`:
- Каждый существующий кластер с **минимум двумя** корректными нормализованными участниками — ровно одна единица `(kind="cluster", unit_id=cluster.id)`. Передать **все** тексты его участников в один `ContentUnitInput`. Не вызывать отдельный AI для участников кластера.
- Каждый `FeedItem` без записи в `cluster_items`, имеющий статус `normalized` или `processed`, — отдельная единица `(kind="feed_item", unit_id=item.id)`.
- Публикации `pending`, `failed` и некорректные единицы не отправлять AI; фиксировать пропуски/ошибки. Кластер из одной публикации автоматически не создавать.
- Запуск не фильтрует AI-кандидатов по `user_sources`. Повторные запуски разных пользователей не должны дублировать готовые результаты.

Не считать единицу актуальной **только** по `processing_status=processed` или непустому тексту `summary`. Истина об актуальности — проверенный снимок и метаданные через существующий репозиторий (отпечаток входа, происхождение summary, версия/конфигурация результатов).

При неизменном входе и конфигурации повторный запуск не должен делать повторных платных вызовов; использовать штатное повторное использование `SummarizationService` / `ImportanceService`. При новом источнике, изменении публикации, состава кластера, summary или значимой конфигурации соответствующий анализ должен быть выполнен заново. Для масштабирования предусмотреть детерминированный обход и ограничение количества обрабатываемых единиц за запуск без изменения семантики существующего `--limit`.

### 3.2. Вызов AI и транзакции

- После кластеризации **сначала выполнить commit**, затем перейти к AI. Нельзя делать `await` сетевого провайдера внутри сессии/транзакции нормализации или кластеризации.
- Переиспользовать `ContentUnitAnalysisUseCase` с явным `kind`; вызвать операции `summary` и `importance` **по отдельности**. Создание адаптеров — аналог уже существующего ручного CLI `app.ai.analyze_feed_item`; без копирования промптов, fingerprint-логики или SQL сохранения.
- Для общего AI не передавать `user_id`/список интересов в `ContentUnitAnalysisUseCase`: `--user` относится к сбору. Для персонального этапа вызывать **готовый DB-backed интерфейс ITD-86** с `kind`/`unit_id`, который сам находит пользователей и читает их интересы из БД. Не реализовывать персональную оценку заново и не использовать `operation="all"` для общего этапа.
- Использовать уже предусмотренные краткие транзакции чтения и условной записи, stale-кандидаты и ограниченный повтор в use case. `STALE_CANDIDATE`, `FAILED`, `NOT_FOUND` и `SKIPPED` не означают успешного завершения.
- Не подменять ошибку одного провайдера успешным результатом и не терять промежуточно сохранённый актуальный `summary` при ошибке `importance`. Следующий запуск должен иметь возможность продолжить, используя актуальное summary.
- Не форсировать запросы (`force=False`) по умолчанию, не выполнять скрытых безлимитных повторов и не держать БД заблокированной во время внешних запросов.

### 3.3. Постановка персональной оценки в Celery (контракт ITD-86)

После успешной записи актуальной общей выжимки единицы (и в стандартном пути — после завершения общей importance) инициировать ровно один вызов:

```python
from app.workers.tasks import score_content_unit_for_eligible_users_task
score_content_unit_for_eligible_users_task.delay(kind, unit_id)
```

Это готовая точка входа из `docs/user-interests.md` ITD-86. Она в отдельном Celery task находит подходящих пользователей и ставит для каждого задачу `relevance.score_user_content_unit`. Воркеры используют уже реализованный `UserRelevanceService`, условное сохранение и `PostgresAdvisoryLock` для защиты от гонок. Результаты сохраняются в `user_item_scores`, а не в общих `FeedItem`/`ContentCluster`.

- **Единица:** только итоговый singleton или кластер; участникам кластера задачи не отправлять.
- **Выбор пользователей:** по включённым источникам текущей единицы и непустым `user_interests`; если список пуст, не ставить платную персональную оценку и не приравнивать отсутствие оценки к 0.
- **Момент:** после commit общей summary. Доступность importance не является техническим требованием самой relevance, но порядок стадий конвейера — summary → importance → постановка relevance.
- **Асинхронность:** запуск конвейера подтверждает постановку задачи в брокер, но **не обещает**, что персональная оценка уже рассчитана к его завершению. Не вызывать массовую персональную оценку синхронно внутри API/цикла конвейера.
- **Надёжность:** ошибки постановки в Redis должны быть видны отдельно и не отменять успешное сохранение общих результатов. Повторы/идемпотентность и корректная повторная постановка после ошибки брокера должны иметь тестовое покрытие; успешный `processed` **не означает** успешную персональную оценку всех пользователей.
- **Только ITD-86:** не менять модель интересов, интерфейс пользовательского просмотра, правила обратной связи или ранжирование ленты.

### 3.4. Семантика `processing_status`

`processed` устанавливается **только после того**, как для одной единицы контента обе операции `summary` и `importance` успешно сохранены как актуальные:
- `feed_item` → `processed` у этой публикации;
- `cluster` → `processed` у всех её актуальных участников.

У `ContentCluster` собственного `processing_status` нет; создание такой колонки не требуется. Финальная запись статуса должна проверять актуальное членство и результаты, чтобы кластер, изменившийся между AI-вызовом и записью, не был ошибочно помечен обработанным. Предпочтительно дать эту проверку небольшому методу в существующем репозитории, а не дублировать в оркестраторе внутренние критерии актуальности.

**Ограничение статуса:** после последующих изменений входа/кластера ранее установленное `processed` может сохраниться, хотя результат уже инвалидирован; поэтому статус сам по себе **не доказательство актуальности**. В этой задаче источником истины остаются AI-метаданные. При выборе кандидатов обязательно обнаруживать такое устаревание и повторно анализировать единицу, не пропуская её из-за статуса. Если понадобится более строгая модель статусов, согласовать её отдельно с учётом всех путей инвалидации.

### 3.5. Ошибки, наблюдаемость и стоимость

- Отказ AI у одной единицы не должен откатывать уже сохранённый сбор/кластеризацию и блокировать анализ остальных независимых единиц. Ошибка должна быть видна в итоговой статистике; CLI завершает запуск с ненулевым кодом при неуспехе AI, сохраняя существующее правило ошибки сбора.
- Не печатать исходные тексты, секреты, ключи и пользовательские интересы в логах. Логировать `kind`, `unit_id`, операции, статусы и безопасную категорию ошибки.
- В `PipelineResult` и выводе CLI дополнительно отражать минимум: количество выбранных, успешно завершённых, переиспользованных/не требующих сетевого запроса, неуспешных и пропущенных единиц; различать ошибки summary и importance, а также успешную/неуспешную **постановку** relevance в очередь. Факт постановки не равен завершённой персональной оценке. Не смешивать показатели нормализации и AI.
- Автоматическая обработка может быть платной. Сохранять отсутствие сетевых вызовов в `--dry-run` и `--fixture`, предусмотреть отдельный управляемый лимит количества AI-единиц на запуск (например, `--ai-limit N`, не меняя `--limit`) и не добавлять автоматический конкурентный fan-out без отдельного решения. Для полного прохода без ограничения нужно явно учитывать стоимость в пользовательской документации.
- Настройки моделей/провайдеров берутся из существующего `Settings`. Отсутствие корректного API-ключа должно дать видимую ошибку AI-этапа, а не ложный `processed`.

## 4. Совместимость и границы изменений

Основные точки реализации: новый модуль под `backend/app/pipeline/` для выбора и последовательного анализа единиц, вызов из `run_pipeline` **после commit**, дополнение `PipelineResult` и вывода `__main__.py`; при необходимости минимальный метод в `ContentUnitAnalysisRepository` для атомарного подтверждения завершения и обновления статусов. После общей обработки — тонкий интеграционный вызов в Celery-API ITD-86. Не дублировать его реализацию.

Существующие алгоритмы `normalize_pending`, `apply_extracted_entities`, `cluster_feed`, сервисы AI и их политики не переписывать. Таблицы уже содержат поля для результатов и статуса; миграция **не предполагается**, если реализация не обнаружит конкретной необходимости.

Нельзя изменять в рамках ITD-85: алгоритмы персонального `relevance`, модель `user_item_scores`, ранжирование, API ленты и дайджестов, авторизацию, UI, Celery/Beat-расписание, алгоритм кластеризации и договорённости о платных моделях. Требуется интеграция с уже готовыми Celery-задачами ITD-86.

### Интеграция с ITD-86 и незавершённая продуктовая часть

В ITD-86 уже реализованы `UserInterest`, миграция `0011_user_interests`, API `/api/users/{user_id}/interests`, `UserRelevanceService`, персональный `user_item_scores`, постановка задач в Celery и проверка актуальности интересов. ITD-85 подключает готовую точку входа **после общей выжимки**, не переписывая эти компоненты. `GET /api/feed` не должен инициировать платные AI-вызовы.

ITD-86 **не реализует** фактический учёт просмотренных карточек: `ViewedStatusProvider` по умолчанию возвращает `None`, и массовая переоценка уже существующего контента при изменении интересов поэтому не выполняется. Это не препятствует оценке нового контента из ITD-85. Интеграция с ITD-89 (feedback) не требуется для текущего контракта.

## 5. Проверки и критерии приёмки

Необходимые сценарии автоматизированных тестов (AI-провайдеры заменяются фейками; реальные платные запросы запрещены):
1. Из двух связанных публикаций — **одна** кластерная summary + importance; у обеих `FeedItem` статус `processed`, без индивидуальных AI-вызовов.
2. Отдельная публикация — один вызов `kind=feed_item`; статус `processed` только после двух успешных операций.
3. Несколько пользователей одного источника — общий контент анализируется один раз; `--user` ограничивает сбор, но не AI-сканирование общей БД.
4. Повторный запуск с неизменёнными входом/конфигурацией — **ноль новых сетевых AI-вызовов**.
5. Добавление участника кластера, изменение primary/текста, изменение версии модели/политики — актуальность пересматривается, устаревшие результаты не выдаются как новые и анализ обновляется на уровне текущей единицы.
6. Переход `FeedItem` из singleton в кластер — отсутствие индивидуального анализа после склейки, сохранение существующих правил инвалидации и проверка гонки с AI-вызовом.
7. Ошибка summary или importance — нет ложного `processed`; другие единицы продолжают обрабатываться; ошибки и частичные результаты отчётны.
8. Проверка атомарности границы: сбой AI после commit не откатывает нормализацию и кластеры; внешние AI-вызовы выполняются без открытых DB-транзакций.
9. `--dry-run` / `--fixture` — нет внешнего AI, записи статусов и необратимых изменений; существующие CLI-варианты продолжают работать.
10. Пустая база, отсутствие включённых источников у пользователя и повторно обрабатываемый глобальный backlog — корректная статистика и коды завершения.
11. После общей выжимки кластера ставится одна задача выбора пользователей, затем отдельные задачи relevance для пользователей с непустыми интересами и доступом к источникам; каждый пользователь получает независимый `user_item_scores`.
12. Нулевые интересы, отключённый источник, изменения интересов во время AI, повторный запуск и неполадки Redis/worker — проверка пропусков, отсутствия ложного нуля, идемпотентности, повторной постановки и сохранения общих результатов.
13. Работоспособность ITD-86 после фактической интеграции проверяется отдельно: mock Celery и PostgreSQL integration; реальные Redis и worker ранее не проверялись совместно с pipeline.

Проверки: `cd backend && uv run ruff check . && uv run pytest`. Для интеграционных проверок PostgreSQL использовать **изолированную тестовую** БД, предварительно применив миграции; действующую пользовательскую или production-БД не менять. Тесты с mock-провайдерами подтверждают маршрутизацию и сохранение, но **не** реальное качество AI и не доступность/стоимость внешних API.

## 6. Открытые операционные вопросы (не блокируют первый коммит спецификации)

- Точный размер/значение по умолчанию для лимита AI-единиц и политика при превышении бюджета, когда появятся реальные объёмы.
- Допускается ли параллельная обработка и нужна ли межпроцессная блокировка для предотвращения одновременных платных запросов из нескольких запущенных конвейеров. Существующее условное сохранение защищает **целостность результатов**, но само по себе не гарантирует оплату каждого AI-вызова только один раз.
- Кто и когда будет планировать регулярные запуски общего конвейера: **Celery Beat** остаётся вне ITD-85. **Celery Worker**, напротив, является нужной частью персонального этапа.
- Способ гарантировать повторную постановку relevance после сбоя брокера между сохранением summary и отправкой задачи (при необходимости — durable outbox), не объявляя простую `.delay()` гарантированной доставкой.

При реализации уточнять эти вопросы по фактической нагрузке, не превращать ITD-85 в переписывание рабочих этапов.
