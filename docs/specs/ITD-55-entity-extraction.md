# ITD-55 — Извлечение сущностей из публикаций

**Статус:** спецификация реализации  
**Задача:** [ITD-55](https://yzcjhacj.yougile.com/team/74c58e471796/#ITD-55)  
**Референс:** [Siftly / lib/rawjson-extractor.ts](https://github.com/viperrcrypto/Siftly/blob/main/lib/rawjson-extractor.ts)

## Цель и границы

Реализовать в Python простой детерминированный извлекатель структурных признаков из **уже нормализованного** `FeedItem` с использованием доступных исходных метаданных `raw_payload`. Результат записывается в существующее поле `FeedItem.extracted_entities` (PostgreSQL JSONB).

Адаптировать подход Siftly к нынешним источникам uPIVO (Telegram, Reddit, YouTube, Habr и универсальный текст публикации). Не переносить специфичный для X/Twitter код или организацию этапов Siftly механически.

ITD-55 отвечает за извлечение и сохранение данных, **но не за то, когда и кем запускается извлекатель**, и не за использование данных далее. Автоматический конвейер, оркестрация, повторный запуск при обновлении публикаций и управление общими статусами — отдельная задача (ITD-53). Парсеры/коннекторы не изменяются.

## Вход и выход

**Вход:** существующий объект `FeedItem` с нормализованными `title`, `body_text` и доступным `raw_payload`. Для платформенно-зависимых правил тип источника передаётся извне (`SourceType`), а не угадывается по ссылке публикации. Отсутствующий, пустой или частично некорректный `raw_payload` не должен ломать извлечение из нормализованного текста.

**Выход:** JSON-совместимый объект для записи в `extracted_entities`:

~~~json
{
  "hashtags": ["python", "ai"],
  "mentions": ["@example"],
  "urls": ["https://github.com/psf/requests"],
  "tools": ["GitHub"],
  "has_media": null,
  "media_types": []
}
~~~

Это **контракт первой версии**; значения примера иллюстративны. `null` у `has_media` означает «нет достоверных метаданных о наличии медиа», а не «медиа отсутствуют». Пустой `media_types` означает отсутствие достоверно распознанных типов.

### Семантика полей

| Поле | Значение | Источник |
| --- | --- | --- |
| `hashtags: string[]` | Явно указанные хештеги публикации; без `#`, нормализованный регистр | Структурные метаданные и текст |
| `mentions: string[]` | Явные ссылки на аккаунты/пользователей: например, `@handle`, `u/handle`. Сохранять различающий платформу синтаксис, не путать с email | Структурные метаданные и текст |
| `urls: string[]` | URL, **упомянутые в содержимом** (включая раскрытые ссылки из метаданных); не URL самой публикации | Текст и метаданные |
| `tools: string[]` | Имена распознанных по ссылкам известных сервисов/продуктов; это подсказки, **не** утверждение, что публикация посвящена им | Сопоставление `urls` со словарём |
| `has_media: boolean / null` | Достоверное наличие/отсутствие медиа либо неизвестность | Только явные исходные метаданные |
| `media_types: string[]` | Известные типы вложений (например, `photo`, `video`, `gif`), если явно доступны | Только исходные метаданные |

Все массивы дедуплицируются с сохранением первого появления; порядок детерминирован. Не добавлять вымышленные значения, когда в данных отсутствуют признаки.

**Не сохраняем в первой версии:**
- `linked_resources`: дублирует `urls`; конкретный тип ресурса/ID можно получить из URL позднее.
- `domains`: однозначно вычисляется из `urls` при необходимости.
- `tweetType`: специфично для X/Twitter и не имеет общего эквивалента для текущих источников.
- `source_tags`/`hubs` как дополнительные копии: теги и хабы Habr уже находятся в `raw_payload`; сами по себе они **не являются хештегами**.
- Имена произвольно упомянутых компаний, людей и моделей, если их нельзя достоверно извлечь из явных структурных признаков без NLP/LLM.

## Правила извлечения

1. Использовать `title` и `body_text` нормализованного FeedItem. Если `raw_payload` содержит явные списки хештегов, упоминаний, ссылок или медиа, учитывать их, не дублируя текстовые находки.
2. Поддержать распространённые URL в обычном тексте и Markdown/HTML-представлениях **в пределах уже доступного содержимого**; не загружать страницы, не делать сетевые запросы и не менять нормализатор.
3. Распознавать хештеги и аккаунтные упоминания с учётом Unicode, границ слова и синтаксиса площадки. Не принимать обычный адрес электронной почты за `@mention`.
4. Для ссылок использовать валидные URL (включая явные раскрытые URL из метаданных), аккуратно отделять завершающую пунктуацию и убирать повторения. Поле `original_url` — адрес самой публикации; **не** считать его автоматически упомянутой ссылкой и не выводить из него `tools`.
5. Перенести принцип словаря известных доменов Siftly, выбрав нужные записи. Проверять **точное совпадение хоста** или поддомен с границей точки; `fakegithub.com` не равен `github.com`. Правила, относящиеся к конкретному пути, проверять по пути URL, а не по одному hostname. Не заявлять о распознавании продукта по одному текстовому упоминанию, если ссылки нет.
6. Для `has_media` и `media_types` полагаться на реальные структурные признаки источника. Если парсер не сохранил сведения о вложениях, оставлять `has_media=null`, а не делать вывод по отсутствию поля.
7. Не смешивать платформенные теги/хабы с текстовыми хештегами. Можно извлечь текстовый `#tag` из статьи Habr; нельзя автоматически превращать `raw_payload.tags` или `raw_payload.hubs` в `hashtags`.
8. Результат чистого извлечения зависит только от входных данных и версии правил/словаря. Не использовать LLM, embeddings, внешние API, БД или побочные эффекты внутри извлекателя.

## Размещение и сохранение

- Реализация извлекателя — `backend/app/processing/extractors/` (модуль уже зарезервирован). Предусмотреть вызываемую Python-функцию для одного FeedItem; сигнатура может быть уточнена при реализации без изменения семантики контракта.
- Отдельный тонкий слой записи присваивает результат в `FeedItem.extracted_entities` через существующий SQLAlchemy ORM. Не создавать новых таблиц и миграций; поле JSONB уже есть.
- Коммит/откат транзакции выполняет вызывающий слой по принятому в проекте правилу.
- Для ранее нормализованных строк должна существовать возможность **явного** вызова заполнения, в том числе повторного. Это не требование к автоматическому расписанию или воркеру.
- `extracted_entities IS NULL` — извлечение ещё не выполнено; JSON-объект с пустыми массивами — выполнено, сущностей не найдено. Повторное выполнение с теми же входными данными не меняет смысл результата.
- На этом этапе **не** изменять `raw_payload`, нормализованные поля, `content_hash`, `summary`, `importance_score`, `processing_status`; отдельно не сбрасывать AI-результаты.
- Вопросы, когда сбрасывать или пересчитывать устаревшие сущности после обновления `raw_payload`, относятся к общему конвейеру. Извлекатель обязан корректно работать при явном повторном вызове.

## Проверки при реализации

Обязательны unit-тесты без LLM, сети и БД для чистого извлекателя; проверка записи — отдельно:

1. Telegram: `#хештег`, `@handle`, URL в тексте; отсутствие медиа-метаданных не превращается в `false`.
2. Reddit: URL из явных полей и текста, `u/username`, `r/subreddit` — не смешивать аккаунты и сообщества; проверить, какие метаданные доступны фактически.
3. YouTube: текст названия/описания, текст субтитров при наличии, ссылки; ссылка самого видео не становится инструментом `YouTube` автоматически.
4. Habr: `raw_payload.tags` и `hubs` не становятся `hashtags`; явно написанный в тексте хештег извлекается.
5. Ссылки: дедупликация, завершающая пунктуация, невалидные URL, ложные совпадения доменов и путь-специфичные домены.
6. Пустой/частичный/неожиданный `raw_payload`, Unicode, совпадающие сущности из текста и метаданных.
7. Повторный вызов на той же публикации даёт одинаковый JSON; запись не трогает остальные поля.
8. Нет зависимости от AI-провайдера, коннектора, общего конвейера и внешних запросов.

## Вне рамок ITD-55

- Сбор, доработка парсеров, реконструкция исходных метаданных, обновление публикаций у коннекторов.
- Автоматическая активация, очереди, Celery/Beat, управление статусами и повторными запусками конвейера (ITD-53).
- Изменения алгоритма дедупликации/кластеризации (ветка `cursor/content-clusters-e741`, PR #6); на момент написания он использует `content_hash`, `title` и `body_text`, **не** `extracted_entities`.
- Изменения суммаризации/оценки важности/релевантности (ITD-17). Отдельная ветка AI уже содержит `extracted_entities` во входных DTO, но интеграция и использование полей в prompt не входят в данную задачу.
- Переработка API поиска/ленты, интерфейса и других потребителей.

## Критерий готовности

Нормализованный FeedItem можно явно передать в новый извлекатель и сохранить детерминированный, корректный JSON в существующее `extracted_entities`, без LLM и изменений соседних стадий; поведение проверено на существующих типах источников и граничных случаях.
