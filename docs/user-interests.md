# Интересы пользователя и персональная релевантность

ITD-86 добавляет необязательный глобальный список интересов пользователя в свободной
форме, CRUD API и DB-backed путь уже существующей AI-оценки персональной релевантности.
Интересы — это один список на пользователя, общий для всех его включённых источников.
Они не являются папками `folders` или темами `topics` и не меняют их поведение.
Алгоритмы ленты, дайджеста, `rank_score`, snapshots, кластеризация, сбор и авторизация
этой задачей не изменяются.

## Необязательность интересов

Ноль интересов — штатное состояние. Суммаризированные материалы из включённых
источников доступны без персональной фильтрации, а персональная оценка **не
запускается**: пустой список — это «оценка не нужна», а не `relevance_score = 0`.
Это осознанная подготовка к будущей персонализации по реакциям, которая в ITD-86
не реализуется.

## Модель данных

Таблица `user_interests` (миграция `0011_user_interests` после `0010_digest_items_snapshot`):

| Поле | Назначение |
| --- | --- |
| `id` | PK |
| `user_id` | FK `users.id`, `ON DELETE CASCADE` |
| `text` | непустой текст интереса |
| `created_at` | дата создания |
| `updated_at` | дата изменения текста, если он менялся |

Ограничения обеспечивает БД, а не только сервис:

- `CHECK (length(btrim(text)) > 0)` — пустая или пробельная строка невозможна;
- уникальный индекс `(user_id, lower(btrim(text)))` — регистр и крайние пробелы не
  создают вторую запись даже при конкурентных запросах;
- индекс по `user_id`.

Сервис дополнительно обрезает крайние пробелы и проверяет дубликат до вставки, чтобы
вернуть понятный `409`, но решение принимает уникальный индекс: `IntegrityError`
превращается в `409` без второй строки.

Список читается в устойчивом порядке по `id`; именно этот порядок входит в
`interests_input_fingerprint`. Перестановка без фактического изменения списка не
провоцирует переоценку. Таблица `user_item_scores` используется повторно: отдельной
таблицы оценок по каждому интересу нет.

## HTTP API

Префикс — `/api/users/{user_id}/interests`. Авторизации нет: `user_id` — это
существующий `users.id`; сервис проверяет принадлежность интересов пользователю,
поэтому чужой `interest_id` недоступен.

| Метод и путь | Результат |
| --- | --- |
| `GET /` | полный список интересов, включая `[]` |
| `POST /` | `201` и созданная запись по `{"text": "..."}` |
| `PATCH /{interest_id}` | замена текста, обновлённая запись |
| `DELETE /{interest_id}` | `204` |

Ответ объекта: `id`, `user_id`, `text`, `created_at`, `updated_at`. Неизвестный
пользователь или интерес этого пользователя — `404`, невалидный текст — `422`,
дубликат — `409`. `PATCH` с тем же нормализованным текстом не меняет `updated_at`,
не инвалидирует оценки и не запускает пересчёт.

## Изменение интересов и актуальность оценок

Фактическое изменение списка (`POST`, `PATCH` с новым текстом, `DELETE`) в той же
транзакции:

1. блокирует строку `users`, сериализуя изменение списка и сохранение оценки этого
   пользователя;
2. инвалидирует текущие персональные оценки пользователя: `relevance_score`
   становится `NULL` (не нулём), `last_good` получает статус `stale`, сам результат
   остаётся в истории метаданных;
3. после commit вызывает узкий хук фонового пересчёта.

Удаление всех интересов инвалидирует оценки так же; платных пересчётов при этом нет,
новые единицы просто не оцениваются.

## DB-backed оценка

`app/services/user_relevance.py` — программный контракт ITD-86:

- `UserRelevanceService.load_user_interests(user_id)` — полный список в устойчивом
  порядке;
- `UserRelevanceService.score_user_content_unit(user_id, kind, unit_id)` — оценка одной
  единицы контента для одного пользователя;
- `UserRelevanceService.score_content_unit_for_eligible_users(kind, unit_id)` — постановка
  фоновых задач для пользователей с включённым источником этой единицы и непустыми
  интересами;
- `UserRelevanceService.recalculate_unviewed_for_user(user_id)` — пересчёт только
  непросмотренных единиц (нужен `ViewedStatusProvider`);
- `UserRelevanceService.recalculate_unviewed_source_for_user(user_id, source_id)` — то же
  в границах одного источника.

Правила оценки:

- единица контента берётся из БД через существующие `ContentUnitAnalysisUseCase` и
  `RelevanceService`; общая выжимка должна быть актуальной, иначе — `skip` без AI;
- `FeedItem` внутри кластера перенаправляется на кластер: оценивается одна общая
  выжимка кластера, участники отдельно не оцениваются;
- оценка возможна, только если у пользователя включён хотя бы один источник единицы;
  для кластера достаточно одного участника из включённого источника — остальные
  участники могут быть из источников, не подключённых пользователем;
- пустой список интересов — `skip` без вызова `JevRelevanceAdapter`;
- повторный вызов с теми же выжимкой и списком интересов переиспользует актуальный
  результат без второго внешнего запроса;
- ошибка AI у одного пользователя не мешает другим и не превращается в
  `relevance_score = 0`.

### Защита от гонки с изменением интересов

`InterestGuardedRepository` (подкласс `ContentUnitAnalysisRepository`) в транзакции
сохранения:

1. блокирует строку `users`;
2. повторно проверяет право пользователя на единицу через включённые источники;
3. сравнивает переданный `interests_fingerprint` с отпечатком текущего списка из БД.

Устаревший ответ не становится `current`: сохранение возвращает `stale_candidate`,
сервис перечитывает интересы и повторяет оценку с актуальным списком (ограниченное
число попыток). `ContentUnitAnalysisUseCase` в этом пути вызывается с `max_attempts=1`:
внутренний повтор с заведомо старым списком только тратил бы платный AI-вызов, поэтому
актуальность перечитывает внешний цикл. Существующая защита по fingerprint выжимки
сохраняется, а CLI по-прежнему использует стандартные две попытки.

### Дедупликация параллельных оценок

`PostgresAdvisoryLock` берёт `pg_try_advisory_lock(int4, int4)` по паре
«пользователь + единица» на отдельном соединении в режиме `AUTOCOMMIT`, без открытой
транзакции, и освобождает блокировку в `finally`. Поэтому блокировка не удерживается
во время AI-ожидания транзакцией записи, а второй параллельный запуск получает
`skip`. Redis-блокировки и таблицы задач не вводятся.

## Просмотренность и экономный пересчёт

Учёт просмотров в ITD-86 **не реализуется**: нет таблицы доставок/показов, карточки
ленты и дайджеста не помечаются просмотренными, API ленты/дайджеста не изменяются.

`app/services/viewed_status.py` объявляет узкий контракт будущего источника статуса:

```python
class ViewedStatusProvider(Protocol):
    def was_viewed(self, user_id: int, kind: Literal["feed_item", "cluster"], unit_id: int) -> bool: ...
```

Правило отбора отделено от источника признака:

- `True` — просмотрено, при изменении интересов не пересчитываем;
- `False` — не просмотрено, пересчёт допустим;
- провайдер не подключён — статус неизвестен, массового ретроспективного пересчёта нет.

`UnviewedCandidateSelector` отбирает единицы из сейчас включённых источников с
актуальной выжимкой, для которых провайдер вернул «не просмотрено». Просмотренный
кластер исключает и своих участников: члены кластера кандидатами не являются.
Исторические дайджесты и `items_snapshot` не переписываются.

Пока провайдера нет, новые единицы всё равно оцениваются по действующим интересам:
хуки изменения интересов и активации источника ничего не ставят в очередь. Будущий
адаптер подключается через единый `get_viewed_status_provider()`
(`app/services/viewed_status.py`): его используют и HTTP-хуки, и фабрика сервиса внутри
Celery-задач. По умолчанию функция возвращает `None`; изменение этой зависимости само
по себе не запускает пересчёт истории.

## Фоновые задачи

`app/workers/scheduler.py` ставит задачи Celery, `app/workers/tasks.py` их выполняет:

| Имя задачи | Назначение |
| --- | --- |
| `relevance.score_user_content_unit` | оценка одной единицы для одного пользователя |
| `relevance.score_content_unit_for_eligible_users` | постановка оценок для подходящих пользователей |
| `relevance.recalculate_user` | пересчёт непросмотренных единиц пользователя |
| `relevance.recalculate_user_source` | пересчёт непросмотренного после активации источника |

HTTP-запрос и изменение интересов только ставят задачи; AI-вызовы выполняет worker.
Хуки устойчивы к недоступности брокера: ошибка планирования логируется и не отменяет
уже сохранённое изменение интересов или источника. При активации источника хук
срабатывает только на фактическое подключение или повторное включение и не меняет
глобальные записи публикаций.

## Стык с ITD-85

ITD-86 даёт данные и механизм персональной оценки; ITD-85 (реализован в
`app/pipeline/analysis.py`) запускает его в автоматическом конвейере **после
готовности общей выжимки** и не дублирует сбор, нормализацию, извлечение сущностей
или кластеризацию.

Порядок шагов на единицу контента: `summary` → `importance` → `processed` с
commit → одна постановка диспетчера → квитанция постановки в AI-метаданные
единицы. Квитанция привязана к отпечатку входа и происхождению выжимки, поэтому
после смены входа/состава/summary она не совпадает и следующий запуск повторяет
только постановку, переиспользуя `summary`/`importance`. Сбой брокера не
откатывает общие результаты и `processed`: ошибка постановки считается отдельно
(`queue_failed`), ошибка записи квитанции — `receipt_failed`; обе дают
ненулевой код CLI. Сбой между постановкой и записью квитанции приводит к
повторной постановке. Доставка задачи не гарантируется, а `processed` по-прежнему
не означает готовую персональную оценку.

Точка входа после сохранения общей выжимки единицы:

```python
from app.workers.tasks import score_content_unit_for_eligible_users_task

score_content_unit_for_eligible_users_task.delay(kind, unit_id)  # kind: "feed_item" | "cluster"
```

Тот же вызов без Celery — `UserRelevanceService.score_content_unit_for_eligible_users(kind, unit_id)`.
Контракт:

- вызывать один раз на единицу контента (`ContentCluster`, если публикация в кластере, иначе
  `FeedItem`) после `summary`; для участников кластера отдельные вызовы не нужны;
- передавать именно `kind`/`unit_id` готовой единицы: `score_user_content_unit` сам
  перенаправит публикацию внутри кластера на кластер;
- не вызывать этот интерфейс внутри HTTP-запроса на N пользователей — он ставит задачи;
- общая важность остаётся независимой от пользователя и интересов; персональная
  оценка не заменяет суммаризацию;
- повторная готовность той же выжимки не должна приводить к повторному внешнему
  запросу: актуальный результат переиспользуется.

## Проверки

Из каталога `backend`:

```sh
uv run python -m pytest tests/test_user_interests_api.py tests/test_user_interest_relevance.py
uv run python -m ruff check --config pyproject.toml app tests alembic
```

Интеграционные проверки на PostgreSQL (`tests/test_user_interests_postgres.py`)
запускаются только с `ITD86_TEST_DATABASE_URL` на одноразовую БД `itd86_interests_test*`
и без него пропускаются; внешние AI-провайдеры в тестах не вызываются.

Общий прогон из корня репозитория: `python start.py --check` (ruff и pytest без
контейнеров).
