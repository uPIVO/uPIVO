# Локальный демостенд

Эта конфигурация предназначена для ветки `deploy/local-demo`. Она запускает отдельный Compose-проект `upivo-demo`, не меняя рабочее окружение `upivo`. Переносить настройки стенда в `main` не требуется.

## Настройка

В каталоге отдельного worktree выполните `cp .env.example .env`. Файл `.env` не хранится в Git. Задайте независимые случайные `POSTGRES_PASSWORD` и `AUTH_TOKEN_SECRET` (для секрета авторизации не менее 32 символов). Для генерации каждого значения можно использовать `openssl rand -hex 32`. Пароль БД должен быть пригоден для URL; шестнадцатеричное значение подходит.

Перенесите существующие `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `TELEGRAM_SESSION` без создания новой Telegram-сессии. Укажите отдельные ключи провайдеров с ограниченным бюджетом. Провайдеры summary, importance и relevance настраиваются независимо: одного ключа может быть недостаточно. Не копируйте весь рабочий `.env`: он может вернуть рабочие порты и подключения.

## Запуск

Из каталога worktree выполните единую команду (можно также указать абсолютный путь к скрипту):

```bash
python3 start_prod.py
```

Требуются macOS, Python 3, установленный Docker Desktop с Docker Compose, ngrok с уже настроенной авторизацией и заполненный `.env`. Скрипт сам открывает Docker Desktop при необходимости, ждёт Docker, собирает и поднимает `upivo-demo` с worker/Beat, отдельно поднимает шлюз и проверяет HTTP-доступ. Он устанавливает или использует LaunchAgent ngrok, не создавая вторую копию исправного туннеля. Блокировка не допускает параллельных запусков скрипта. Файлы `.env`, ключи, Telegram-сессия и флаги AI не меняются; ручной платный конвейер не запускается.

Успех означает готовность локального API и публичного Swagger; ошибки сети/ngrok возвращают ненулевой код и не удаляют работающие контейнеры или данные. Доступность старого сервиса на 8765 проверяется отдельно; скрипт его не устанавливает и не перезапускает. Существующие источники обрабатываются по уже настроенному расписанию. Для проверки реальной обработки AI нужен отдельный согласованный прогон.

API, PostgreSQL, Redis, worker, Beat и Nginx имеют `restart: unless-stopped`: Docker восстанавливает завершившиеся контейнеры, кроме остановленных вручную. Это не перезапуск зависшего процесса и не восстановление удалённого через `down` контейнера. Автозапуск самого Docker Desktop и всего стенда после входа скрипт не устанавливает; после перезагрузки достаточно снова выполнить `python3 start_prod.py`. Полный цикл перезагрузки Mac отдельно не проверялся.

После запуска шлюза Swagger доступен по http://127.0.0.1:18080/upivo/docs. Прямой порт API 18000 используется для health и подключения шлюза; Swagger открывайте через префикс /upivo. PostgreSQL и Redis доступны только локально на портах 15432 и 16379. Порты API 18000 и шлюза 18080 фиксированы для этой схемы; порты PostgreSQL и Redis можно изменить в `.env`. Внутри контейнеров API использует сервисы `postgres:5432` и `redis:6379`; изменения локальных DATABASE_URL и REDIS_URL это не переопределяют. Миграции применяются перед запуском API. Данные БД хранятся в отдельном volume проекта, а не в рабочей базе.

Автоматический сбор и автоматический платный AI по умолчанию выключены. Это не запрещает платные вызовы из ручных API-запросов и не является денежной квотой. После настройки ключей и бюджета включите `SCHEDULED_PIPELINE_ENABLED=true`; `SCHEDULED_PAID_AI_ENABLED=true` включайте только для согласованного автоматического AI. Фоновые процессы запускаются командой `docker compose --profile workers up -d --build`. После изменения `.env` пересоздайте затронутые сервисы через `up -d`, а не только `restart`.

## Общий шлюз и публичная ссылка

Шлюз хранится в `gateway/`, но запускается отдельным Compose-проектом `upivo-gateway`. Он не останавливается вместе с `upivo-demo`. Nginx слушает только `127.0.0.1:18080` на Mac. Из контейнера адреса `host.docker.internal:8765` и `host.docker.internal:18000` ведут к опубликованным портам Mac (Docker Desktop). Перенос на Linux требует отдельной проверки сети.

```bash
docker compose -f gateway/compose.yml config --quiet
docker compose -f gateway/compose.yml up -d
```

Запросы `/upivo/…` направляются в uPIVO с удалением `/upivo`; все остальные пути передаются существующему сервису на порту 8765 без изменения пути. Префикс `/upivo` резервируется за uPIVO. Для корректных ссылок Swagger API запущен с `--root-path /upivo`. Он доверяет proxy-заголовкам; доступ к опубликованному порту должен оставаться только локальным. Проверяйте работу обоих сервисов перед переключением ngrok.

ngrok направляет существующий HTTPS-домен на порт шлюза. Для автоматического запуска после входа и восстановления при завершении процесса используется отдельный LaunchAgent `local.upivo-gateway.ngrok`, установленный в `~/Library/LaunchAgents/`. Его исходный шаблон — `gateway/local.upivo-gateway.ngrok.plist.example`; при установке `__HOME__` заменяется абсолютным домашним каталогом, `__NGROK_BIN__` — результатом `command -v ngrok`. Журналы: `~/Library/Logs/upivo-gateway/ngrok.log`. Каталог журналов создаётся перед загрузкой службы. `KeepAlive=true` включает восстановление, `ThrottleInterval=30` ограничивает частоту запусков. Планового перезапуска исправного процесса нет. Авторизация ngrok берётся из существующей локальной конфигурации, без копирования authtoken в Git или plist.

Старую службу `local.doska-chatgpt.ngrok` необходимо отключить через `launchctl disable gui/$(id -u)/local.doska-chatgpt.ngrok` и выгрузить, прежде чем загружать новую. Сам сервис `local.doska-chatgpt.bridge` не останавливается. Новая служба загружается командой `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/local.upivo-gateway.ngrok.plist`; обе службы ngrok одновременно запускать нельзя. Замена туннеля кратко прерывает внешний доступ и открытые соединения.

Проверка состояния: `launchctl print gui/$(id -u)/local.upivo-gateway.ngrok`. Перезапуск вручную при необходимости: `launchctl kickstart -k gui/$(id -u)/local.upivo-gateway.ngrok`. Не используйте старую команду `background.py start/restart` как управление общим туннелем: она относится к прежней паре служб Doska. Для ручного запуска без LaunchAgent сначала выгрузите новый job, затем используйте `ngrok http http://127.0.0.1:18080 --inspect=false`.

LaunchAgent запускается после входа пользователя, а не до входа при загрузке Mac. Он восстанавливает завершившийся процесс, но не диагностирует зависший процесс или недоступность upstream. Единый `start_prod.py` запускает Docker Desktop, шлюз и приложения по запросу; автоматически после входа настроен только ngrok. Без работающего шлюза/приложения туннель не обеспечивает доступ к нему.

Публичный Swagger: `https://<ваш-ngrok-домен>/upivo/docs`; эту ссылку используйте в QR-коде. Старые ссылки остаются прежними, кроме зарезервированного `/upivo`. Не публикуйте порты PostgreSQL и Redis. Для ngrok нужен настроенный аккаунт и authtoken; токен не хранится в репозитории.

Туннель и Nginx не заменяют авторизацию и контроль расходов. В этой конфигурации новый rate limiter не добавлен. Ручные платные запросы могут расходовать бюджет ключей. Бесплатный ngrok имеет квоты и может показывать страницу предупреждения перед Swagger.

Компьютер, Docker, шлюз и ngrok должны оставаться включёнными; сон компьютера прерывает доступ. Шлюз — общая точка отказа обоих сервисов. Исходящие подключения к Telegram и моделям используют сеть компьютера или VPN, а не туннель ngrok.

## Остановка

Для остановки только uPIVO выполните `docker compose --profile workers down`. Общий шлюз и ngrok оставьте работающими, если они нужны существующему сервису. Данные БД сохранятся. Не добавляйте `-v`, если данные нужно сохранить. Старое окружение запускайте только из его собственного каталога с его конфигурацией. Остановка общего шлюза: `docker compose -f gateway/compose.yml down` — внешний доступ к обоим сервисам прекратится. Не останавливайте общий ngrok без учёта второго сервиса.
