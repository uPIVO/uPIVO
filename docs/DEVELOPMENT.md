# Ежедневная разработка

Python-команды выполняются из `backend/`, Compose-команды — из корня.
После обновления файлов проекта:

```bash
cd backend
uv sync --locked
uv run alembic upgrade head
```

База должна работать. Если работаете только в Docker, из корня выполните
`docker compose up --build -d --wait`: зависимости и миграции обновятся.

Добавление зависимости:

```bash
uv add package-name
uv add --dev package-name
```

Выберите одну команду по назначению зависимости. uv обновляет pyproject.toml и uv.lock
вместе. Для обновления существующей зависимости: `uv lock --upgrade-package package-name`,
затем `uv sync --locked`; проверьте изменения и тесты.

## Изменение схемы

Alembic хранит версии структуры базы данных. Migration задаёт последовательность
изменений; upgrade применяет новые версии. Исходная migration пустая и фиксирует baseline.

Добавьте ORM-модель в `app/models`, наследуйте Base из `app.db.base`, импортируйте
модель в `app/models/__init__.py`, чтобы Alembic видел metadata. Затем:

```bash
uv run alembic revision --autogenerate -m "description"
uv run alembic upgrade head
uv run alembic current
uv run alembic check
```

Autogenerate создаёт черновик: проверьте вручную upgrade/downgrade, особенно переименования
и удаление данных. Не меняйте уже применённые командой migrations; добавляйте новые.
Для проверки отката на своей одноразовой БД: `uv run alembic downgrade -1`, затем upgrade.
Не выполняйте откат на общей БД без согласования. Обновляйте модель вместе с её миграцией.

## Проверки и запуск

```bash
uv run uvicorn app.main:app --reload
```

В другом терминале из backend:

```bash
uv run ruff check .
uv run pytest
```

Для форматирования: `uv run ruff format .`. Большинство тестов не требуют живой БД;
успех/ошибка DB endpoint проверяются через override session. Тесты кластерного
анализа и миграции снимков требуют `ITD17_TEST_DATABASE_URL` на отдельную PostgreSQL-базу
с именем `itd17_cluster_test*` и предварительный `alembic upgrade head` на этой базе.
Без переменной эти тесты пропускаются. CI поднимает такую БД и запускает весь набор
после миграций. Не воспринимайте mock-тест как проверку соединения.
Тест миграции сам создаёт и удаляет дополнительную одноразовую БД; тестовой роли
нужно право `CREATEDB`. Он проверяет сохранение всех старых данных и транзакционный
откат при ошибке переноса.
Интеграционные тесты обратной связи требуют `ITD89_TEST_DATABASE_URL` на отдельную
БД `itd89_feedback_test*`; они сами применяют и откатывают миграцию `0012_feedback`.
Подробности — в [документации обратной связи](feedback.md).

Куда класть код — см. [границы модулей](ARCHITECTURE.md). Не добавляйте новый слой,
пока у него нет понятной задачи. Connector и extractor создаются отдельными задачами.

## Celery worker локально (macOS)

`start.py` поднимает только PostgreSQL и Redis через Docker (или Podman), применяет
миграции и запускает **локальный** API через uvicorn. Worker он не запускает: обычный
worker — отдельный процесс в другом терминале.

```bash
# из backend/, при поднятых Postgres и Redis и применённых миграциях
uv run celery -A app.workers.celery_app:celery_app worker --loglevel=INFO --concurrency=2
```

Пул по умолчанию (`prefork`) на нативном macOS с Python 3.12 работает: проект
подключает совместимую инициализацию дочерних процессов (`app/workers/worker_init.py`).
`--pool=solo` не нужен и не должен использоваться как обходной путь. Начиная с
Celery 5.6.3 и billiard 4.3.0 macOS стартует процессы пула через `spawn`, и Celery
включает trace-оптимизации только для перезапуска через `execv`; без обработчика
`worker_process_init` первая же задача падала бы до своего тела с
`ValueError: not enough values to unpack (expected 3, got 0)` в
`celery.app.trace.fast_trace_task`. Проект вызывает штатный
`celery.app.trace.setup_worker_optimizations` для текущего app дочернего процесса
только при фактическом `billiard.get_start_method() == "spawn"`; при fork/forkserver
поведение не меняется. Это локальная совместимость проекта с установленной версией
Celery, а не утверждение об исправлении в upstream: при обновлении celery/billiard
проверьте, нужен ли обработчик. С `--pool=solo` задачи выполняются в процессе
родителя и эта инициализация не участвует.

API в Docker и локальный API не смешивайте: у контейнера свой `DATABASE_URL`
(`postgres:5432` внутри compose) и свой рабочий каталог, а локальный uvicorn и
worker работают с `.env` текущего checkout. Запускайте либо compose-профиль API,
либо локальный `python start.py`; worker подключайте к тому же Redis/PostgreSQL,
что и API, с которым вы его используете.

## Автоматический сбор по расписанию (ITD-84)

Celery Beat ставит одну общую задачу `pipeline.run_scheduled`, Worker исполняет её
через `asyncio.run(run_shared_pipeline(...))`. Проход опрашивает **каждый
уникальный источник** с хотя бы одной включённой подпиской ровно один раз, затем
нормализует накопившиеся публикации, извлекает сущности, склеивает кластеры и
коммитит их. После commit выполняется существующий общий AI-этап
(`run_common_analysis`) и его штатная асинхронная постановка персональной оценки —
это **полный автоматический конвейер**, включая платные Summary/Importance.

Решение продукта от 2026-10-29: полный автоматический AI разрешён **без**
контроллера расходов, жёсткой денежной квоты нет. Автоматический проход вызывает
`run_common_analysis` с `ai_limit=None`, то есть обрабатывает **весь** накопившийся
backlog, а не первые 50 единиц: `ai_limit` остаётся техническим пределом одного
запуска и не является бюджетом. Учёт фактических расходов, глобальный бюджет и
пользовательские квоты — отдельная будущая работа (ITD-84, раздел 4.4); пока они
не сделаны, расходы автоматического прохода денежно не ограничены.

Ручной `python -m app.pipeline --user` сохраняет прежнее поведение (свой
`--ai-limit`, по умолчанию 50).

Переменные окружения (см. `.env.example`):

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `SCHEDULED_PIPELINE_ENABLED` | `false` | Явный переключатель запуска расписания Beat |
| `SCHEDULED_PIPELINE_INTERVAL_SECONDS` | `1800` | Интервал в секундах, UTC |
| `SCHEDULED_PIPELINE_SOURCE_LIMIT` | не задано (`None`) | Необязательный операционный лимит публикаций **на источник** в сборе/нормализации scheduled-прохода; не `ai_limit` и не бюджет |
| `SCHEDULED_PAID_AI_ENABLED` | `true` | Полный автоматический AI; `false` — только бесплатные стадии, без AI и постановки Relevance |

`SCHEDULED_PIPELINE_SOURCE_LIMIT` действует только на сбор: он передаётся как
`limit` в `run_shared_pipeline`, а не в `run_common_analysis`. `None` (по
умолчанию) сохраняет обычное production-поведение (лимиты платформ/коннекторов).
Значение должно быть положительным целым; пустое значение в `.env` не задают —
удалите строку целиком.

При `SCHEDULED_PIPELINE_ENABLED=false` расписание пустое: Beat ничего не ставит,
ручной CLI и персональные relevance-задачи работают как раньше. Значение
`SCHEDULED_PAID_AI_ENABLED=true` действует только на запуски Worker'а;
`SCHEDULED_PAID_AI_ENABLED=false` — сознательный opt-out: сбор, нормализация,
сущности и кластеризация выполняются, а AI и постановка relevance пропускаются с
причиной `paid_ai_disabled`.

Обновление `.env`: уже развёрнутые пользовательские runtime `.env` этим
изменением не меняются и не перезаписываются; чтобы получить полный auto AI на
расписании, нужно явно включить `SCHEDULED_PIPELINE_ENABLED=true` (и, если там
было выставлено `SCHEDULED_PAID_AI_ENABLED=false`, поменять его на `true`), после
чего перезапустить worker и beat.

```bash
# API и инфраструктура
docker compose up -d --build
# Scheduled worker и ровно один Beat
docker compose --profile workers up -d --build
docker compose logs -f worker beat
```

Профиль `workers` сохранён. Worker и Beat ждут готовности PostgreSQL и Redis и
успешного завершения сервиса `migrate`; оба перезапускаются при сбое
(`restart: unless-stopped`). Beat должен быть **один** на расписание: несколько
экземпляров поставят одну и ту же задачу несколько раз.

### Одновременность и восстановление

Полный общий проход один: перед стартом берётся сессионный advisory lock
PostgreSQL (`pg_try_advisory_lock` с фиксированным пространством имён) на
выделенном физическом соединении в режиме `AUTOCOMMIT`, вне транзакций конвейера.
Ручной реальный запуск и запуск по расписанию используют одну и ту же блокировку.

- Блокировка занята: проход пропускается со статусом `skipped_locked` (CLI
  возвращает код 3), второй сбор не запускается.
- Успех или падение: `pg_advisory_unlock` и закрытие выделенного соединения в
  `finally`; соединение выводится из пула, поэтому пул не отдаст его вместе с
  захваченным lock.
- Разрыв соединения: блокировку снимает сам сервер при завершении сессии, а
  конвейер проверяет соединение и владение между стадиями и по таймеру, пока
  ждёт завершения асинхронной стадии. Потеря блокировки прерывает проход
  (`PipelineLockLost`); автоматического повторного захвата и продолжения «как
  будто ничего не было» нет.
- Граница гарантии: это координация через общий сервер PostgreSQL, а не
  распределённый fencing. Строгого прерывания синхронной стадии нет: сбор
  Telegram/Reddit/YouTube/Habr — блокирующие вызовы, которые не отдают
  управление event loop, поэтому после потери блокировки успевают завершиться
  текущие вызовы источников (в том числе несколько подряд) до первой проверки
  между стадиями. При сетевом разделении между worker'ом и PostgreSQL уже
  начатый внешний HTTP-вызов отменить нельзя; спасение данных обеспечивают
  короткие транзакции и коммит каждой страницы/источника.

Сбой одного источника не отменяет остальные: результат по каждому источнику
пишется отдельно, ошибки перечислены в `failed_sources` результата задачи, а
накопленный backlog обрабатывается следующим проходом. Ошибки AI/Redis видны
отдельно в счётчиках `ai`/`queue_*`.

### Проверка расписания на живом стенде

Планировщик проверяется только реальным Beat: он должен сам инициировать
`pipeline.run_scheduled` через Redis, а Worker — выполнить проход на реальных
PostgreSQL/Redis и провайдерах. Прямой вызов `run_shared_pipeline` или ручной CLI
подменяют планировщик и не являются проверкой Beat. Для ограниченного прогона
используйте `SCHEDULED_PIPELINE_INTERVAL_SECONDS` (укороченный интервал) и
`SCHEDULED_PIPELINE_SOURCE_LIMIT` (например, `10`), а после первой due-постановки
свой Beat останавливайте, чтобы получился ровно один проход.

### Реальный PostgreSQL для advisory lock

Регресс порядка `execution_options`/`detach` unit-stub ловит не полностью:
проверка на живом сервере выполняется env-gated тестом одноразовой БД
(production не используется):

```bash
ITD84_TEST_DATABASE_URL='postgresql+psycopg://...' uv run pytest tests/test_pipeline_lock_postgres.py
```

Без переменной тесты пропускаются. Они проверяют запрет `execution_options` после
`detach` (именно этот `AttributeError` из SQLAlchemy 2.0 ломал реальный запуск),
конкуренцию, освобождение lock, отсутствие соединений в пуле и физическое
закрытие после сбоя чтения pid.

### Наблюдаемость

Логи (logger `app.pipeline.run`) содержат `run_id`, `trigger`
(`manual`/`schedule`), длительность, число источников и статусы, суммарные
счётчики публикаций (`fetched`/`saved`/`inserted`/`updated`), число
нормализованных публикаций, кластеров, ошибки по источникам, счётчики AI и
постановок relevance, причины пропуска (`skipped_locked`, `paid_ai_disabled`,
`skipped_disabled`). Тексты публикаций, ключи и prompt'ы не логируются. Задача
возвращает компактный JSON со статистикой.

```bash
# Ручной запуск той же задачи через Worker, без ожидания расписания
docker compose --profile workers exec worker celery -A app.workers.celery_app:celery_app call pipeline.run_scheduled
```

Ограничение стоимости: `--ai-limit` (по умолчанию 50) — технический предел
единиц за один ручной запуск, а не денежный бюджет. Журнал фактических расходов,
глобальный жёсткий бюджет и пользовательские квоты остаются отдельными задачами
ITD-84 (раздел 4.4).

## Парсер YouTube

Сбор сырых видео с публичного канала через RSS (feedparser, без API-ключа).
Нужны PostgreSQL и `alembic upgrade head`. Из `backend/`:

```bash
uv run python -m app.connectors.youtube "https://www.youtube.com/@GoogleDevelopers"
```

Без записи в БД: добавьте `--dry-run`. Несколько последних роликов (обычно до 15)
пишутся в `sources` + `feed_items` (название, ссылка, дата, описание).
Если у ролика есть субтитры — их текст кладётся в `body_text` и в `raw_payload.transcript`;
если субтитров нет, сохраняется описание, ролик всё равно пишется.
Повторный запуск обновляет те же `external_id`. Субтитры с YouTube не качаются снова,
если текст уже лежит в `raw_payload.transcript`. Пустой канал — source и 0 записей.
Неверный URL завершает процесс с кодом 2; сеть/HTTP — с кодом 1.
Не принимаются search, playlist, watch и OAuth.

## Habr

Предпросмотр свежих статей доступен через `GET /api/habr/preview?limit=3` после
запуска API. Он загружает полный текст, а при недоступности статьи использует
текст из списка публикаций. `HabrService` в `backend/app/services/habr.py` можно
вызвать из backend-кода с обычной SQLAlchemy `Session`; он записывает статьи в
общие таблицы `sources` и `feed_items`. Для предпросмотра база данных не нужна.
`POST /api/habr/sync` с JSON `{"pages": 1}` запускает сохранение, а
`GET /api/habr/saved` показывает сохранённые статьи. Для этих запросов нужна БД.
Если статьи получены, но ни одну не удалось обработать, предпросмотр возвращает
HTTP 502; ошибки отдельных статей записываются в лог.

## Reddit

Предпросмотр и сохранение публикаций subreddit запускаются отдельными CLI-командами.
Публикации попадают в общие `sources` и `feed_items`, а временной курсор хранится

## Нормализация контента

После сбора сырых `feed_items` приводит `raw_payload` к полям
title / body_text / original_url / author / published_at и считает `content_hash`
(SHA-256 нормализованных title+body, 64 hex-символа). `raw_payload` не меняется.
Статус: pending → normalized или failed. Пустой/битый payload и отсутствие URL —
failed; title/author/дата могут быть пустыми.

Пример без БД, из `backend/`:

```bash
uv run python -m app.processing --fixture tests/fixtures/normalize/sample.json
```

Pending-строки в PostgreSQL (нужны миграции, `alembic upgrade head`):

```bash
uv run python -m app.processing
```

`--dry-run` печатает результат без commit. `--limit N` и `--item-id ID` сужают выборку.

## Сбор под пользователя

Основной запуск синхронизирует каждый источник с хотя бы одной включённой связью
`user_sources` один раз, независимо от числа подписчиков. Поддерживаются YouTube,
Telegram, Reddit и Habr; публикации остаются в общих `feed_items`.
`--user` синхронизирует только включённые источники выбранного пользователя через
общий dispatcher; источники других пользователей не опрашиваются. Основной запуск
без `--user` по-прежнему собирает каждый DISTINCT enabled Source один раз. Сбор
не проверяет пароль: пользователь задаётся id или email. Feed/Digest HTTP API только
читает сохранённые публикации и не запускает collection.

Нужны PostgreSQL и `alembic upgrade head`. Пользователь и связи `user_sources`
должны уже быть в базе. Учётную запись можно создать через
`POST /api/auth/register`. Для локального сборщика достаточно строки `users`;
хеш при сборе не проверяется:

```sql
INSERT INTO users (email, password_hash)
VALUES ('demo@example.com', 'local-dev-not-auth');
-- source_id — строка из sources, например после python -m app.connectors.youtube
INSERT INTO user_sources (user_id, source_id) VALUES (1, 1);
```

Из `backend/`:

```bash
uv run python -m app.services --user demo@example.com
uv run python -m app.services --user 1
```

Нет источников / все выключены — `sources=0`, код 0. Неизвестный пользователь — код 2.
Пустой fetch источника — `status=empty`; ошибка сбора — `status=failed`, код 1.
Нормализация запускается отдельно: `uv run python -m app.processing`.

## Дедупликация и склейка инфоповодов

После сбора (и, если хеш ещё нужен, после нормализации) одинаковые и близкие
публикации становятся одним инфоповодом. Строки `feed_items` не удаляются.
Миграция `0006_content_clusters` добавляет `content_clusters` и `cluster_items`.
Миграция `0008_cluster_item_constraints` запрещает членство одного FeedItem в двух
кластерах и более одного primary в кластере; существующие некорректные данные
приведут к явной ошибке миграции.

Точный дубль — одинаковый непустой `content_hash`. Если хеш пустой, тот же
очищенный title + body тоже считается точным дублем. Разные тексты об одном
событии сравниваются только по title и body_text: оценка
`0.8 * cosine(слова заголовка) + 0.2 * cosine(слова текста)`, порог `0.55`,
и в заголовках должно быть минимум 2 общих содержательных слова. Почти дословное
тело (cosine ≥ 0.85 и 12+ общих слов) склеивается даже при разных заголовках.
Лексическое совпадение применяется только к публикациям с разницей дат не более
7 дней (когда обе даты известны); точные дубли могут объединяться независимо от даты.
Лексическая связь также проверяется со всеми участниками соединяемых групп,
чтобы один промежуточный материал не склеил разные события.
Короткий повторяющийся футер не склеивает ролики. Summary и importance не
читаются и могут быть пустыми. Одиночная публикация не получает кластер.

В кластере один `is_primary`: самый длинный очищенный `body_text`, при равенстве
более новый `published_at`. `content_clusters.title` берётся из primary.
`content_clusters.summary` остаётся пустым; повторный запуск не создаёт вторую
строку кластера и не затирает summary, если оно уже было.

Пример без БД, из `backend/`:

```bash
uv run python -m app.clustering --fixture tests/fixtures/cluster/sample.json
```

Все нормализованные или полностью обработанные `feed_items` в PostgreSQL
(`alembic upgrade head`):

```bash
uv run python -m app.clustering
uv run python -m app.clustering --dry-run
```

Печать: id кластера, id primary, заголовки, пометка `exact` или `similar`.
`--dry-run` не пишет строки. Пустая лента — `clusters=0`. Неверный fixture — код 2,
ошибка БД — код 1.

## Конвейер публикаций

Один запуск для пользователя, у которого источники уже включены: сбор сырья,
нормализация pending `feed_items`, извлечение сущностей в `extracted_entities`,
склейка в `content_clusters` / `cluster_items`, затем общий AI-этап и постановка
персональной оценки по интересам.
Этапы не переписываются, вызываются как есть. Нормализация, склейка и AI-этап
смотрят на общую ленту `feed_items`, как отдельные команды `app.processing` и
`app.clustering`, а не только на строки этого пользователя: `--user` задаёт только
область сбора. Извлечение тоже смотрит на все нормализованные публикации общей БД.
Повторный запуск идемпотентен: сбор обновляет те же `external_id`, нормализация
берёт только `pending`, склейка обновляет уже существующие кластеры, а AI-этап
переиспользует актуальные результаты и не делает повторных платных вызовов. Нет
включённых источников — сбор не вызывается, остальные этапы общей ленты всё
равно выполняются.

Ручной запуск и запуск по расписанию (см. выше) делят **одни и те же** глобальные
стадии: `run_pipeline` собирает источники пользователя, `run_shared_pipeline` —
все активные, а нормализация, извлечение сущностей, склейка и общий AI-этап
выполняются одной реализацией (`app/pipeline/run.py`). Оба реальных запуска
берут общую блокировку прохода: если она занята, CLI печатает `skipped_locked` и
возвращает код 3, не запуская второй сбор. `--dry-run` блокировку не берёт, так
как ничего не пишет.

Общий AI-этап живёт в `app/pipeline/analysis.py` и работает после commit
нормализации и склейки, без открытой транзакции на время внешних вызовов. Он
последовательно обходит все единицы контента в детерминированном порядке
(сначала кластеры по id, затем одиночные публикации по id) и для каждой единицы
выполняет операции `summary` и `importance` через `ContentUnitAnalysisUseCase`,
подтверждает `processed` участникам, ставит ровно одну задачу
`relevance.score_content_unit_for_eligible_users` в брокер и записывает квитанцию
постановки в AI-метаданные единицы; каждое успешное подтверждение `processed`
очищает квитанцию, поэтому выбранная единица всегда ожидает постановки после
commit. Участники кластера отдельно не анализируются, фильтра по источникам
пользователя нет. Единицы с актуальной квитанцией лимит не занимают; единица без
квитанции или с устаревшей квитанцией переставляет задачу без платных вызовов.
Подробнее о контрактах — [документация AI](ai-summarization.md) и
[интересы](user-interests.md).

Обработка платная: каждый новый AI-вызов расходует кредиты провайдеров, а
постановка задачи в брокер не означает готовую персональную оценку — её считает
Celery worker позже. `--ai-limit` ограничивает число единиц за запуск и не связан
с `--limit` (он ограничивает сбор и pending-нормализацию). Программный вызов
`run_pipeline(..., ai_limit=None)` делает явный полный проход по backlog — его
стоимость растёт линейно с числом необработанных единиц.

Нужны PostgreSQL, `alembic upgrade head` и доступный Redis для постановки задач.
Пользователь и `user_sources` — как для `python -m app.services --user`. Из
`backend/`:

```bash
uv run python -m app.pipeline --user demo@example.com
uv run python -m app.pipeline --user 1 --limit 5
uv run python -m app.pipeline --user 1 --ai-limit 10
uv run python -m app.pipeline --user 1 --dry-run
uv run python -m app.pipeline --fixture tests/fixtures/pipeline/sample.json
```

`--dry-run` не опрашивает источники, откатывает нормализацию, извлечение и
склейку и не вызывает AI. `--fixture` гоняет чистые шаги без базы и тоже без AI.
Печать включает отдельную статистику AI-этапа: `ai_selected`, `ai_succeeded`,
`ai_reused`, `ai_failed`, `ai_skipped`, `ai_summary_failed`,
`ai_importance_failed`, `queue_succeeded`, `queue_failed`, `receipt_failed`.
Неизвестный
пользователь — код 2. Занятая блокировка общего прохода — код 3. Ошибка сбора —
код 1, после того как pending-строки уже нормализованы и склеены. Ошибка AI, постановки в очередь или записи квитанции —
тоже код 1, при сохранённых общих результатах. Нет `--user` и нет `--fixture` —
код 2.

## Регистрация и вход

`POST /api/auth/register` создаёт `users` по email и паролю. В `password_hash`
хранится scrypt-хеш, не пароль. Пароль короче 8 символов — HTTP 422. Повторный
email, без учёта регистра — HTTP 409 `{"detail":"Email already registered"}`.

`POST /api/auth/login` проверяет пару и возвращает подписанный токен
(`token`, `token_type: bearer`, `user_id`, `email`). Неверный email или пароль —
401 `{"detail":"Invalid email or password"}` без различения существования аккаунта.
Задайте в локальном `.env` случайный `AUTH_TOKEN_SECRET` длиной минимум 32 символа
(например, результат `python -c "import secrets; print(secrets.token_urlsafe(48))"`).
Без секрета вход и проверка токена возвращают 503; общего dev-секрета нет.
Не публикуйте этот секрет. Смена секрета инвалидирует выданные токены.

Передавайте `Authorization: Bearer <token>` на все пользовательские API:
sources, topics, interests, feedback, feed, digests, favorites и Habr.
Для старых контрактов `user_id` в пути/query/body должен совпасть с токеном.
Избранное определяет пользователя только по токену.
Без токена, с недействительным токеном или после удаления аккаунта — 401;
с чужим `user_id` — 403. Регистрация, вход и health остаются открытыми.

Из `backend/`, API уже запущен (`uv run uvicorn app.main:app --reload`):

```bash
curl -s -X POST http://127.0.0.1:8000/api/auth/register \
  -H 'content-type: application/json' \
  -d '{"email":"demo@example.com","password":"correct-horse"}'
curl -s -X POST http://127.0.0.1:8000/api/auth/login \
  -H 'content-type: application/json' \
  -d '{"email":"demo@example.com","password":"correct-horse"}'
```

## Темы и источники

HTTP API управляет связями `user_sources` и тематическими папками `folders` /
`feed_item_folders`. В пути передаётся существующий `users.id`, а заголовок
`Authorization: Bearer` должен нести токен этого же пользователя из
`POST /api/auth/login`.

Источник общий: повторное подключение того же канала не создаёт вторую строку
`sources`, а только связь пользователя. Выключение меняет `user_sources.enabled`.
`DELETE /api/users/{user_id}/sources/{source_id}` удаляет только связь, сохраняя
общий Source и публикации. Для YouTube достаточно URL с id канала
(`https://www.youtube.com/channel/UC...`); этот запрос канал не скачивает.
Для Telegram ID канала записывается в общий `Source` при первой синхронизации.
Тема — папка общей ленты. В неё кладётся id публикации из `feed_items`, без копии
материала и без избранного.

Нужны PostgreSQL и `uv run alembic upgrade head`. Пользователя можно
зарегистрировать через `POST /api/auth/register` или вставить строку для
маршрутов, которые не проверяют пароль:

```sql
INSERT INTO users (email, password_hash)
VALUES ('demo@example.com', 'local-dev-not-auth');
```

Из `backend/`, в другом терминале после `uv run uvicorn app.main:app --reload`:

```bash
curl -s -X POST "http://127.0.0.1:8000/api/users/1/sources" \
  -H "content-type: application/json" \
  -H "Authorization: Bearer <token from POST /api/auth/login>" \
  -d '{"type":"youtube","url":"https://www.youtube.com/channel/UC_x5XG1OV2P6uZZ5FSM9Ttw","name":"Google for Developers"}'
```

Неизвестный пользователь — HTTP 404. Пустой список источников или тем — `[]`.

## Лента и дайджесты

После миграций API читает уже сохранённые `feed_items`; запрос ленты или дайджеста
не запускает сбор источников. `GET /api/feed?user_id=1` показывает публикации со
статусом `normalized` или `processed` из включённых источников пользователя.
`GET /api/feed/{item_id}?user_id=1` также проверяет, что публикация принадлежит
включённому источнику этого пользователя.
`POST /api/digests/generate` с телом
`{"user_id": 1, "type": "general", "period_hours": 24}` сохраняет дайджест.
Настройки пользователя доступны через `GET /api/digests/settings` и
`PUT /api/digests/settings` с bearer token. Без query `user_id` используется
пользователь из токена; чужой `user_id` запрещён. Например, тело PUT
`{"period_hours": 72, "max_items": 10}` задаёт окно отбора и число карточек.
Можно передать только одно поле; остальные настройки сохраняются.
По умолчанию используются 24 часа и 15 карточек; диапазоны — 1–168 и 1–100.
Один кластер считается одной карточкой. Явные `period_hours` и `max_items`
в запросе генерации имеют приоритет только для этого дайджеста и не изменяют
сохранённые настройки. Это окно отбора, а не расписание автоматической генерации
или интервал сбора Beat. Для хранения настроек требуется миграция
`0015_digest_settings`; её downgrade удаляет только таблицу настроек.

Его текст и карточки сохраняются как снимок: поздние изменения публикаций,
источников и кластера не меняют `GET /api/digests/{digest_id}`. Если в кластер
добавилась новая публикация, следующий дайджест может включить обновлённую карточку
кластера. В её состав входят публикации, прошедшие фильтры периода, темы и включённых
источников, в том числе уже показанные участники этого кластера.
Миграция `0010_digest_items_snapshot` фиксирует ранее созданные
дайджесты в их состоянии на момент миграции; восстановить их вид на исходную
дату создания из старой схемы невозможно.
При обновлении остановите старый API, выполните `alembic upgrade head` и запустите
новую версию: после миграции `items_snapshot` обязателен для новых дайджестов.
Downgrade `0010` блокируется при наличии дайджестов, чтобы не удалить их снимки.
Просмотр и переключение избранного у дайджеста требуют `user_id` в query и
проверяют принадлежность дайджеста указанному пользователю.
Для тематического дайджеста укажите `type=topic` и строку `topic`.

Параметр `topic` в ленте и дайджесте сейчас ищет слова в тексте, summary и тегах
публикации; он не фильтрует по папкам `folders`. Папки редактируются отдельно
через `/api/users/{user_id}/topics` с Bearer-токеном владельца.

## Проверка интеграции третьего спринта

`uv run alembic upgrade head` применяет обе ветви миграций и объединяющую
`0014_sprint3_heads`. Старые миграции не переписаны. Не откатывайте таблицы
спринта на рабочей БД: обычный downgrade удаляет таблицы соответствующей фичи.

Для полного тестового прогона нужны **одноразовые** PostgreSQL и Redis.
Задайте URL отдельных PostgreSQL-баз: `ITD17_TEST_DATABASE_URL`
(имя `itd17_cluster_test*`), `ITD86_TEST_DATABASE_URL` (`itd86_interests_test*`),
`ITD89_TEST_DATABASE_URL` (`itd89_feedback_test*`), а также `ITD84_TEST_DATABASE_URL`.
Роль тестов должна иметь CREATEDB. `SPRINT3_TEST_REDIS_URL` должен указывать
на отдельный тестовый Redis, который не обслуживает реальные очереди.

```bash
uv run ruff check .
uv run pytest
uv run alembic check
```

`test_sprint3_runtime.py` поднимает настоящий Celery Worker (solo) и процесс Beat,
проверяет общую загрузку для двух пользователей, нормализацию, кластеризацию,
общий AI-анализ, персональные оценки, ранжирование, избранное, обратную связь
и неизменяемый дайджест через FastAPI. Внешний Habr HTTP и платные AI-провайдеры
заменены фейками; это не проверка доступности поставщиков или реальных ключей.
`test_sprint3_migration_postgres.py` сравнивает данные и снимки до/после upgrade
с `0010`, а также downgrade/re-upgrade на одноразовой БД.

Ограничения: нет учёта просмотров, поэтому ретроспективный пересчёт интересов
пока пропускается. Новые материалы оцениваются по текущим интересам.
Нет outbox и гарантии доставки при потере сообщения Redis. Ошибка персональной
оценки повторяется до трёх раз, затем видна как failed в Worker.
Перед публичным развёртыванием нужны HTTPS, rate limiting регистрации/входа,
политика отзыва токенов и контроль расходов AI; текущая проверка их не заменяет.

## Использование GPT

Для всех трёх AI-операций задайте `LLM_PROVIDER=openai`,
`IMPORTANCE_PROVIDER=openai`, `RELEVANCE_PROVIDER=openai`, `OPENAI_API_KEY`
и `OPENAI_MODEL` в своём `.env`, затем перезапустите API/Worker/Beat.
Можно переключить лишь одну операцию, сохранив остальные на OpenRouter/Jev.
[Полная конфигурация и CLI](ai-summarization.md#gpt-через-openai-responses-api).
Миграций и новых зависимостей для OpenAI нет. `test_ai_openai.py` использует
HTTP mocks; `test_sprint3_runtime.py` проверяет оба варианта конвейера с настоящими
PostgreSQL, Redis и Worker/Beat, подменяя только внешний HTTP OpenAI для GPT-варианта.
