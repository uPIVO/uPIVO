# Ручная суммаризация единиц контента

Этап 1 ITD-17 предоставляет контракт суммаризации, не зависящий от конкретного провайдера, и адаптер OpenRouter. Единица состоит из одной или нескольких нормализованных публикаций и обязательно имеет явный `kind`: `feed_item` содержит ровно одну публикацию с тем же ID, `cluster` — не менее двух публикаций с разными ID. Операция суммаризации не читает и не изменяет базу данных, ORM-модели или `processing_status`. JSON-вход обязан содержать `kind`; старые файлы без него нужно обновить, вид единицы не выводится из количества публикаций.

## Настройка

Настройки читаются из корневого `.env` через `app.core.config.Settings`. Пример безопасных имён параметров находится в корневом `.env.example`:

- `LLM_PROVIDER=openrouter` — единственный провайдер, реализованный на этапе 1;
- `LLM_API_KEY` — секретный ключ OpenRouter; не добавляйте ключ в Git и не передавайте его в логи;
- `LLM_BASE_URL=https://openrouter.ai/api/v1` — базовый URL API, совместимого с OpenAI; допускается только HTTPS;
- `LLM_MODEL=@preset/deep-seek-v4-flash-via-direct-deep-seek-provider` — идентификатор пользовательского пресета OpenRouter, передаваемый параметром `model`; значение можно изменить настройкой;
- `LLM_TIMEOUT_SECONDS=60` — конечный таймаут запроса (допустимый диапазон: больше 0 и не более 300 секунд).

Файл `backend/app/ai/analysis_policy.toml` — единственный источник точных инструкций и критериев для summary, relevance и importance; в нём же заданы версии prompt. Загрузчик на стандартном `tomllib` проверяет обязательные секции, непустые строки и шкалы importance с 5/5/3 критериями до сетевого вызова. Стандартная политика загружается и кэшируется один раз на процесс; автоматического перечитывания нет, поэтому после её изменения перезапустите процесс. Адаптеры принимают типизированную политику при явной сборке для теста или приложения, не меняя кэш.

Модель по умолчанию берётся из `Settings` (значения `.env.example`: `LLM_MODEL` и `TYPESAFE_MODEL`); Settings загружается обычным `get_settings()` один раз. Необязательный CLI-флаг `--model` (команды без БД) и флаги `--summary-model` / `--importance-model` / `--relevance-model` (FeedItem-команда) переопределяют соответствующую модель только на данный запуск через конструктор адаптера; они не меняют Settings, `.env` или другие операции. Пустое переопределение отклоняется. Остальные настройки провайдера, адреса и таймаута остаются из Settings. Backend не собирается как wheel (`package = false`); Docker копирует исходный каталог целиком, включая TOML-политику.

При ручной сборке прикладных сервисов опциональные значения модели передаются тем же конструкторным аргументом; `None` оставляет значение из Settings. Это пример передачи необязательных значений, а не новые обязательные ключи конфигурации:

~~~python
from app.ai.analysis_policy import load_analysis_policy
from app.ai.importance import ImportanceService
from app.ai.jev import JevImportanceAdapter, JevRelevanceAdapter
from app.ai.openrouter import OpenRouterAdapter
from app.ai.service import RelevanceService, SummarizationService
from app.core.config import get_settings

settings = get_settings()
policy = load_analysis_policy()
summary_model: str | None = None
relevance_model: str | None = None
importance_model: str | None = None

summarization_service = SummarizationService(
    OpenRouterAdapter(settings, model=summary_model, policy=policy)
)
relevance_service = RelevanceService(
    JevRelevanceAdapter(settings, model=relevance_model, policy=policy)
)
importance_service = ImportanceService(
    JevImportanceAdapter(settings, model=importance_model, policy=policy)
)
~~~

Ключ нужно задать только локально в `.env`; этот файл не редактируется автоматически. Для ручного запуска требуется явное решение владельца о реальном запросе: вызов может быть платным. Обычные тесты не обращаются к провайдеру.

## Запуск эксперимента

Из каталога `backend`:

~~~sh
uv run python -m app.ai ../docs/examples/content-unit.json --save-result /tmp/upivo-summary.json
uv run python -m app.ai ../docs/examples/content-unit.json --model "@preset/another-model"
~~~

Команда принимает один JSON-объект `ContentUnitInput`, не открывает БД и печатает выжимку, отпечаток версии, признак повторного использования, время выполнения и доступные сведения об использовании. Токены и стоимость выводятся только если их сообщил провайдер; оценочные значения не подставляются.

Для повторного запуска с теми же входом и настройками передайте ранее сохранённый файл:

~~~sh
uv run python -m app.ai ../docs/examples/content-unit.json \
  --prior-result /tmp/upivo-summary.json \
  --save-result /tmp/upivo-summary.json
~~~

При точном совпадении отпечатка версии можно повторно использовать непустую выжимку без сетевого вызова. Отпечаток включает сериализованный вход, идентификаторы провайдера, базовый URL, выбранный пресет, `summary.prompt_version` и точные тексты политики. При изменении входа, провайдера, base URL, выбранной модели или политики результат генерируется заново. `--force` явно запрашивает новый результат. Файл результата — локальные данные, которым доверяет вызывающая сторона; командная строка проверяет его структуру, непустую выжимку и версию отпечатка. Секреты в отпечаток не входят.

Автоматических платных повторов и молчаливого усечения входа нет. Слишком длинный запрос может быть отклонён провайдером; ошибка не содержит тело ответа или исходный текст. Если `finish_reason` отсутствует, ответ допускается для совместимости; если поле присутствует, принимается только `stop`. Ответы с другой причиной завершения или встроенной ошибкой отклоняются, неполная выжимка не сохраняется как успешный результат.

## Контракт и границы

Публикации передаются адаптеру как JSON с фиксированными именами полей; `raw_payload` в DTO запрещён. Поля `body_text` и `original_url` обязательны и непусты. Остальные сведения, включая `title`, `published_at`, `source_name`, `extracted_entities` и `is_primary`, необязательны. Пустой список публикаций недопустим, одна публикация допустима. Суммаризация использует неперсонализированную инструкцию `content-summary-v2` с приоритетами: сохранность содержания и достоверность, затем ясность, затем компактность. Она убирает повторы и шум без самостоятельной информации, но сохраняет самостоятельные факты, условия, атрибуцию, уникальные сведения и существенные расхождения; не отбирает содержание по важности или пользовательским интересам и не добавляет фактов или рекомендаций. Те же требования действуют для singleton. Текст публикаций считается недоверенным содержимым.

Этапы 2 и 3 добавляют две независимые операции поверх одной и той же готовой общей выжимки: персональную релевантность относительно списка интересов и экспериментальную общую важность без персонализации. Ни одна из них не вызывает суммаризацию автоматически и не работает с базой данных. Повторное использование доступно только через явно переданный файл результата; скрытого процессного кэша нет.

## Хранение анализа FeedItem и ContentCluster (Stage 4)

Репозиторий `app.ai.repository.ContentUnitAnalysisRepository` принимает явную пару `(kind, unit_id)`. Одиночная публикация хранит результат в `feed_items.summary` / `importance_score`; кластер из 2+ публикаций — в `content_clusters.summary` / `importance_score` один раз на всю группу, без копирования участникам. Все исходные тексты передаются суммаризатору одним `ContentUnitInput`; общая важность и персональная релевантность вычисляются по готовой общей выжимке теми же AI-сервисами.

`user_item_scores` содержит либо `feed_item_id`, либо `cluster_id`: XOR-check требует ровно одну цель, отдельные UNIQUE исключают повторные строки пользователя для одной цели. Удаление кластера каскадно удаляет его персональные оценки, но не исходные публикации. `rank_score`, `reason`, `calculated_at` сохранены; правила ранжирования этим компонентом не задаются.

`feed_items.ai_metadata`, `content_clusters.ai_metadata` и `user_item_scores.analysis_metadata` хранят валидированные полные DTO результатов, версии и отпечатки входа. Отпечаток исходного снимка строится по всему сериализованному `ContentUnitInput`, включая `kind`, ID, `body_text`, URL, сущности и `Source.name`, если тот передан; `raw_payload` не загружается. В общей метаинформации не сохраняются API-ключи или исходные пользовательские интересы; для relevance сохраняются только отпечатки. `SummaryResult.fingerprint` остаётся отпечатком входа и конфигурации генерации, а не содержимого результата; DTO и кэш результата суммаризации не меняются. Для привязки importance/relevance к точному тексту используется `summary_lineage_fingerprint`: версия `summary-lineage-v1` хэширует вместе `SummaryResult.fingerprint` и точный `SummaryResult.summary`. Этот отпечаток хранится в метаданных происхождения результата и передаётся при проверке повторного использования предыдущего результата и условной записи; версия JSON-оболочек метаданных повышена до `schema_version=2`, чтобы старую семантику не принять за текущую.

`summary` и оценки — проекции только актуальных результатов. Для каждого вида результата хранится last-good DTO и не более одного отдельно помеченного stale-кандидата: успешное сохранение обновляет last-good, сохраняя старый stale-кандидат; следующая stale-попытка заменяет его. Stale-ответ не публикуется в проекциях. Изменение текста summary инвалидирует зависимые importance/relevance/rank-проекции. Репозиторий не вызывает AI, не фиксирует транзакции, не управляет повторами и не меняет `processing_status`. Отдельный ручной Stage 4 CLI использует этот репозиторий через прикладной use case; он не подключает общий конвейер или Celery. Вызывающая сторона должна использовать короткую отдельную транзакцию чтения, выполнить AI-запрос без открытой сессии, затем в короткой транзакции записи перечитать и заблокировать цель, исходные FeedItem и Source перед условным сохранением. Для кластера сначала блокируется его родительская строка, затем участники в порядке ID; запись членства использует тот же родительский lock и блокировки участников. `raw_payload` не выбирается ни для одного вида единицы.

FeedItem, входящий в кластер, нельзя загрузить для отдельного AI-анализа: вызывающая сторона получает явную ошибку с ID кластера, без неявного перенаправления и без платного запроса. Если членство возникло уже во время запроса, полученный ответ сохраняется только как stale-кандидат. При изменении состава, primary или заголовка кластерные результаты инвалидируются; при включении нового участника инвалидируются его прежние одиночные проекции и персональные оценки. Изменение нормализованных полей обнаруживается повторной сверкой полного отпечатка входа. Сохранённые последние успешные DTO и один stale-кандидат не выдаются как актуальные после изменения входа.

Имя `FeedItemAnalysisRepository` оставлено как совместимый псевдоним общего репозитория. Публикации не удаляются, singleton-кластеры не создаются. Алгоритм кластеризации не изменён: в его слое записи добавлены только согласованные блокировки и инвалидация AI-результатов.

## Ручной анализ единицы контента с сохранением в БД (Stage 4)

Команда `app.ai.analyze_content_unit` принимает `--kind feed_item|cluster` (по умолчанию `feed_item`). Прежнее имя `app.ai.analyze_feed_item` и одиночные вызовы сохранены. Команда не подключена к Celery/автоматической обработке и не меняет `processing_status`. Для запуска БД должна уже содержать миграцию `0009_content_unit_ai_analysis` после интеграционной цепочки `0007` → `0008`. Downgrade `0009` отказывается работать, пока существуют персональные оценки кластеров: их нельзя молча удалить или превратить в FeedItem-оценки. Миграции не запускаются командой анализа: применяйте их отдельно только к явно выбранной тестовой или dev-БД после проверки целевого `DATABASE_URL`. Не применяйте миграцию к production или к БД из локального `.env`, пока её назначение явно не подтверждено; smoke-проверки этого этапа используют отдельную disposable-БД.

Из каталога `backend`, сначала убедившись, что настроенная БД — нужная изолированная dev/test-БД:

~~~sh
uv run python -m app.ai.analyze_content_unit 45 --kind cluster --operation summary
uv run python -m app.ai.analyze_content_unit 45 --kind cluster --operation importance
uv run python -m app.ai.analyze_content_unit 45 --kind cluster --operation all \
  --user-id 42 --interests ../docs/examples/interests.json
uv run python -m app.ai.analyze_feed_item 123 --operation summary
uv run python -m app.ai.analyze_feed_item 123 --operation importance
uv run python -m app.ai.analyze_feed_item 123 --operation relevance \
  --user-id 42 --interests ../docs/examples/interests.json
uv run python -m app.ai.analyze_feed_item 123 --operation all \
  --user-id 42 --interests ../docs/examples/interests.json
uv run python -m app.ai.analyze_feed_item 123 --operation all \
  --user-id 42 --interests ../docs/examples/interests.json \
  --summary-model "@preset/summary-override" \
  --importance-model "jev-importance-override" \
  --relevance-model "jev-relevance-override"
~~~

Операция по умолчанию — `all`; она требует существующий `--user-id` и JSON-массив полного списка `--interests`. `summary` и `importance` не требуют пользовательского контекста. Операция `relevance` (как и отдельная `importance`) использует только уже сохранённую актуальную выжимку и не запускает суммаризацию неявно. `all` сохраняет выжимку и оценивает importance и relevance по одному и тому же точному `SummaryResult`; ошибка провайдера одной оценки не мешает попытке независимой второй оценки. Если условное сохранение обнаружило устаревшие входные данные, зависимые дальнейшие оценки по этой выжимке пропускаются и сценарий анализа начинает ограниченный повтор. Модельный флаг применяется только к выбранной операции; адаптеры невыбранных операций не создаются. В JSON-ответе выводятся статусы, `reused`, число проходов и результаты; текст созданной выжимки выводится намеренно, входной `raw_payload`, список интересов и секреты не печатаются.

Перед запросами проверяются идентификаторы, существование пользователя, текущая выжимка для операций только с оценкой, интересы и конфигурация нужных провайдеров. Каждое чтение или сохранение в БД использует отдельную короткую транзакцию; открытая сессия не переживает `await` провайдера. Условное сохранение может вернуть уже оплаченный ответ как stale-кандидат без публикации проекции. Если при сохранении выжимки обнаружен устаревший вход, зависимые оценки пропускаются; если устаревание выявлено только после начала запроса оценки, его оплаченный ответ сначала сохраняется кандидатом, а следующие зависимые оценки пропускаются. При таком сигнале без другой ошибки сценарий анализа один раз перечитывает свежий снимок и повторяет весь набор запрошенных операций (не более двух проходов); второй платный проход возможен, а флаг `--force` может привести к повторному запросу каждого шага. Ошибки провайдера, авторизации, сети и БД сами по себе не повторяются. Файл интересов и выжимка передаются TypeSafe при relevance, поэтому используйте только данные, разрешённые к отправке внешнему сервису; ошибки и вывод CLI не раскрывают содержимое интересов.

### Граница с конвейером и проверка БД

Вызов AI-этапа из конвейера реализован в ITD-85 (`app.pipeline.analysis`, см.
[руководство по конвейеру](DEVELOPMENT.md)): выбор единиц, отдельные операции `summary` и
`importance`, подтверждение `processed` и одна постановка персональной оценки. Здесь
описаны только контракты единиц и ручные сценарии; правила отбора живут в этапе
конвейера и не дублируются в адаптерах. После успешной постановки персональной оценки
этап хранит в тех же метаданных единицы квитанцию `relevance_dispatch` (отпечаток входа
и `summary_lineage_fingerprint`); поле аддитивное и отсутствует в старых записях. Код,
читающий метаданные через `extra=forbid`, должен обновляться согласованно с pipeline и
worker: прочитать новое поле старым кодом нельзя, поэтому откат только части компонентов
не поддерживается. Прямой прикладной вызов:
`ContentUnitAnalysisUseCase(kind="cluster", ...).run(cluster_id, ...)` из
`app.services.analyze_feed_item`; для одиночных публикаций прежний
`FeedItemAnalysisUseCase` остаётся совместимым входом. Обе операции оценки независимы и не
задают правила отбора.

Адресные PostgreSQL-тесты: `ITD17_TEST_DATABASE_URL=<URL отдельной itd17_cluster_test... БД> pytest tests/test_ai_content_unit_postgres.py -q` после `alembic upgrade head` на этой же одноразовой БД. Без явно заданного тестового URL они пропускаются. Тесты проверяют миграционные ограничения, общую запись без дублирования, инвалидацию при изменении состава и удаление зависимых оценок; реальные AI API не вызываются.

## Персональная релевантность через Jev / TypeSafe

Этап 2 принимает готовую выжимку из файла `SummaryResult` и полный непустой список интересов пользователя. Отдельный `JevRelevanceAdapter` вызывает TypeSafe напрямую и не зависит от `LLM_PROVIDER`, `LLM_API_KEY` или доступности OpenRouter. База данных и повторная суммаризация не используются.

### Настройка

Безопасные имена параметров добавлены в корневой `.env.example`:

- `TYPESAFE_API_KEY` — ключ из TypeSafe console; задайте его только локально в `.env` и не публикуйте;
- `TYPESAFE_BASE_URL=https://api.typesafe.ai` — только HTTPS, без логина, пароля, query и fragment;
- `TYPESAFE_MODEL=jev-1.14.0` — версия модели по умолчанию, можно изменить настройкой;
- `TYPESAFE_TIMEOUT_SECONDS=60` — конечный таймаут больше 0 и не более 300 секунд.

Используется закреплённый ID `jev-1.14.0`, а не подвижный alias; на дату проверки документация TypeSafe указывала `jev-latest` на `jev-1.13.0`, а `jev-preview` — на `jev-1.14.0`. Для стабильного повторного использования указывайте версионный ID: переход alias на другую версию не меняет саму строку настройки и потому не меняет локальный fingerprint. Английский указан основным языком Jev; качество на русских данных следует проверять на собственных примерах.

Запрос отправляется на `POST {TYPESAFE_BASE_URL}/v1/systemone` с `Authorization: Bearer ...`. Тело содержит один вопрос `relevance` типа `noul` и одно состояние с готовой выжимкой и **полным** списком интересов. Ключ TypeSafe независим от OpenRouter; Stage 2 не вызывает Stage 1.

### Ручной запуск

Из каталога `backend`, имея уже сохранённый результат суммаризации:

~~~sh
uv run python -m app.ai.relevance_cli /tmp/upivo-summary.json \
  --interests ../docs/examples/interests.json \
  --save-result /tmp/upivo-relevance.json
uv run python -m app.ai.relevance_cli /tmp/upivo-summary.json \
  --interests ../docs/examples/interests.json \
  --model "jev-relevance-override"
~~~

`/tmp/upivo-summary.json` — файл `SummaryResult`, который сохраняется Stage 1 через `--save-result`; `interests.json` — JSON-массив строк, содержащий весь список интересов. Эта команда отправляет выжимку и интересы TypeSafe и может тарифицироваться по входным токенам. Она не меняет исходный файл суммаризации и не открывает БД. Вывод содержит `relevance`, provider/model, fingerprint, `reused`, время и только доступный usage; текст выжимки и список интересов повторно не печатаются.

Для повторного запуска с явным prior result:

~~~sh
uv run python -m app.ai.relevance_cli /tmp/upivo-summary.json \
  --interests ../docs/examples/interests.json \
  --prior-result /tmp/upivo-relevance.json \
  --save-result /tmp/upivo-relevance.json
~~~

Совпадающий fingerprint позволяет повторно использовать ранее сохранённый результат без API-вызова. Он включает точные строки выжимки и интересов (в указанном порядке), provider, базовый URL, выбранную модель, текст и версию политики; API-ключ в нём отсутствует. `--force` явно запрашивает пересчёт; если он завершится ошибкой, существующий файл результата останется нетронутым. При повторном использовании метаданные модели и usage остаются данными первоначального вызова. Выводится только реально сообщённое API число входных/выходных токенов; стоимость не вычисляется и не подставляется. Скрытого кэша и автоматических повторов запросов нет.

### Семантика и границы

Noul — это вероятность утвердительного ответа, а не градуированная сила релевантности: `0` означает «нет», `1` — «да», значения около `0.5` — неопределённость. Адаптер возвращает число `[0,1]` и не применяет порог, не ранжирует материалы и не выставляет оценку общей важности. Единственный вопрос оценивает, соответствует ли содержание готовой выжимки хотя бы одному интересу; совпадения по остальным темам не требуются. Точный текст инструкции задаётся только в секции `[relevance]` файла `app/ai/analysis_policy.toml` и отправляется провайдеру без переформулировки.

Невалидный вход или ответ, пустой ответ, неверный тип ответа, bool/нечисловое/не конечное значение или число вне `[0,1]` отклоняются без усечения и без вывода исходного текста, ключа либо тела ответа провайдера. Ошибки HTTP, таймаута и транспорта также не включают эти данные. Сведения об использовании берутся только из `usage.input_tokens` и `usage.output_tokens`, если их вернул API.

### Формулировка пользовательских интересов

Текущая оценка Noul использует переданные формулировки интересов и не выясняет скрытое намерение пользователя. Название продукта не означает автоматически интерес ко всем альтернативам или ко всем задачам, которые этот продукт решает. Значение Noul — вероятность утвердительного ответа на заданный вопрос, а не мера корреляции технологий.

Различайте интерес к конкретному продукту и интерес к задаче:
- «Новости и обновления OpenAI Whisper» — интерес к продукту;
- «Распознавание речи, транскрибация аудио и сравнение STT-моделей, включая альтернативы Whisper» — интерес к задаче и альтернативам;
- «Автоматическая транскрибация созвонов и подготовка протоколов совещаний» — интерес к конкретному сценарию, в отличие от неоднозначного «совещания или созвоны»;
- «Личная продуктивность: планирование задач, календарь и привычки» — более определённая формулировка, чем «продуктивность».

При сборе интересов стоит уточнять, важен ли сам продукт, решаемая задача, сценарий применения или поиск альтернатив. Это рекомендация к будущему управлению интересами (ITD-23), а не реализованная нормализация профиля: текущий компонент не расширяет и не переписывает интересы автоматически. Не нужно заменять все узкие интересы широкими: специфический интерес к одному продукту может быть намеренным.

В локальном эксперименте использовался пост о Nemotron 3.5 Super VL — модели для текста, изображений и видео; переданный материал не описывал STT. Поэтому сравнение с интересом «OpenAI Whisper» не проверяет распознавание альтернативных STT-продуктов. Низкий ответ также не доказывает отсутствие связи во всех возможных сценариях. Из единичных примеров нельзя выводить универсальный порог отбора.

## Экспериментальная общая важность через Jev Score

Этап 3 принимает только готовую выжимку из `SummaryResult`. Он не принимает интересы, не вычисляет персональную релевантность, не вызывает повторно Stage 1 и не обращается к БД. Jev получает одну выжимку и три независимых вопроса `score` в одном запросе TypeSafe; цикл отдельных сетевых запросов на вопрос не используется.

Общие инструкции, вопросы, дополнительные инструкции и упорядоченные критерии трёх шкал хранятся только в секции `[importance]` файла `app/ai/analysis_policy.toml`; адаптер передаёт их провайдеру без переформулировки. В шкалах `scale_score` и `significance_score` по пять критериев (значения 0–4), в `reaction_score` — три критерия (0–2). Файл политик не содержит Python-правило вычисления итоговой оценки: веса `1.0/1.0/1.0` и версия агрегации `content-importance-sum-v2` остаются отдельным числовым правилом в `app/ai/importance.py`.

Дробные `score` сохраняются без округления и усечения; значение каждого компонента проверяется по конечному диапазону соответствующей шкалы. В Python вычисляется итог: `scale_score + significance_score + reaction_score`, диапазон `[0, 10]`. Результат сохраняет исходные компоненты, итог, веса и версию агрегации `content-importance-sum-v2`. Сохранённые оценки старой версии не считаются актуальными и требуют пересчёта. Эта формула не задаёт правила персонального ранжирования.

Из каталога `backend`, имея сохранённый `SummaryResult`:

~~~sh
uv run python -m app.ai.importance_cli /tmp/upivo-summary.json \
  --save-result /tmp/upivo-importance.json
uv run python -m app.ai.importance_cli /tmp/upivo-summary.json \
  --model "jev-importance-override"
~~~

CLI принимает только сохранённую выжимку, поддерживает явно переданный `--prior-result`, `--save-result` и `--force`, не перезаписывает файл выжимки и атомарно сохраняет результат. Совпадающий fingerprint повторно использует prior без API-вызова. Fingerprint включает точную выжимку, provider, базовый URL, выбранную модель, содержимое и версию политики, упорядоченные вопросы/критерии, версию агрегации и веса; секрет исключён. Используются настройки `TYPESAFE_*`, описание которых приведено выше; `--model` переопределяет модель только на текущий запуск и не меняет Settings. Ручной запрос к Jev может тарифицироваться; автоматических повторов нет. CLI показывает только полученные от API usage-токены, не выдумывает стоимость и не печатает текст выжимки.

Файл выжимки и полный список интересов отправляются стороннему сервису. [TypeSafe указывает](https://typesafe.ai/legal/privacy-policy), что не обучает модели на пользовательском вводе; та же политика описывает хранение данных, пока это необходимо для услуг/деловой цели, и размещение сервиса в США. [Zero Data Retention](https://docs.typesafe.ai/legal) доступен корпоративным клиентам. Не включайте пользовательские данные в эксперименты без согласования допустимости их передачи.
