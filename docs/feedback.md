# Обратная связь по публикациям и инфоповодам

ITD-89 добавляет явную реакцию пользователя на **отображаемую единицу контента**:
`useful` («полезно») или `not_interested` («неинтересно»). Сервер хранит одну
текущую реакцию на пару «пользователь + единица», её можно заменить или снять.
Реакции сохраняются для будущей персонализации, но в рамках ITD-89 **не влияют**
на ранжирование, `rank_score`, `relevance_score`, `user_interests`, `user_item_scores`,
выдачу и не запускают фоновые задачи.

## Единица оценки

Единица — ровно одно из двух:

- `feed_item` — отдельная публикация `feed_items`, **не входящая** в кластер;
- `cluster` — целый инфоповод `content_clusters`, карточка которого агрегирует
  одну или несколько публикаций.

Оценка кластера не создаёт реакций его участникам, а участника кластера нельзя
оценить как `feed_item` даже на экране деталей. Числовые ID `feed_items.id` и
`content_clusters.id` независимы: тип единицы обязателен и не выводится из `is_cluster`.
Отдельные singleton-кластеры ради реакций не создаются.

## Модель данных

Таблица `feedback` (миграция `0012_feedback` после `0011_user_interests`):

| Поле | Назначение |
| --- | --- |
| `id` | PK, `BIGINT GENERATED ALWAYS AS IDENTITY` |
| `user_id` | FK `users.id`, `ON DELETE CASCADE` |
| `feed_item_id` | FK `feed_items.id`, `ON DELETE CASCADE`, NULL для реакции на кластер |
| `cluster_id` | FK `content_clusters.id`, `ON DELETE CASCADE`, NULL для реакции на публикацию |
| `reaction` | PostgreSQL enum `feedback_type`: `useful`, `not_interested` |
| `created_at` | дата создания текущей реакции |
| `updated_at` | заполняется только при фактической смене реакции |

Ограничения задаёт БД, а не только сервис:

- `CHECK ck_feedback_exactly_one_target` — ровно одна из колонок `feed_item_id` /
  `cluster_id` не NULL (XOR);
- `UNIQUE (user_id, feed_item_id)` и `UNIQUE (user_id, cluster_id)` — одна текущая
  реакция на пару;
- индекс `(user_id, created_at DESC, id DESC)` для списка реакций и отдельные
  индексы по `feed_item_id` / `cluster_id` для каскадной очистки.

Таблиц `feedback_history`, soft-delete, `deleted_at` и журнала реакций нет:
`created_at` и `updated_at` описывают только текущее состояние. Реакции не
дублируются в `raw_payload` или Redis.

## HTTP API

Префикс — `/api/users/{user_id}/feedback`. Авторизации нет: `user_id` — это
существующий `users.id`; это не проверка личности. Чужие реакции API не возвращает
и не меняет.

| Метод и путь | Действие | Успех |
| --- | --- | --- |
| `PUT /{kind}/{unit_id}` | создать или заменить реакцию | `201` новая, `200` имеющаяся |
| `GET /{kind}/{unit_id}` | текущая реакция | `200` |
| `DELETE /{kind}/{unit_id}` | снять реакцию | `204` |
| `GET /` | реакции пользователя | `200`, включая `[]` |

`kind` — только `feed_item` или `cluster`; `user_id` и `unit_id` — положительные
целые. Тело `PUT`: строго `{"reaction": "useful" | "not_interested"}`; лишние поля,
пустой JSON и неизвестные значения — `422`. Ответ: `id`, `user_id`, `kind`,
`unit_id`, `reaction`, `created_at`, `updated_at` — без чужих данных, публикаций,
AI-оценок и истории.

Семантика:

- повторный `PUT` с той же реакцией — `200` без изменения `updated_at` и без дубля;
- другая реакция перезаписывает **ту же строку** и обновляет `updated_at`;
- третьей нейтральной реакции нет: «без оценки» — это `DELETE`;
- `DELETE` физически удаляет только строку `feedback` своего пользователя,
  повторный `DELETE` — `204`;
- отсутствие реакции на `GET` — `404`; это не означает, что публикации нет;
- отсутствующий пользователь — `404` во всех маршрутах.

`GET /` возвращает реакции в порядке `created_at DESC, id DESC` с `limit` (1–100,
по умолчанию 20), `offset` и необязательным `kind`. Для подгрузки оценок конкретных
видимых карточек допускается повторяемый `unit_id` (1–100 значений) **только вместе
с `kind`**: реакции на запрошенные ID приходят одним запросом к БД и без пагинации,
единицы без реакции просто отсутствуют в массиве, повторные ID дедуплицируются.

## Доступность единицы

Оценить можно только карточку, которую может вернуть действующая пользовательская
выдача. Правило вынесено в `app/services/visibility.py` и используется и лентой
(`FeedService`), и обратной связью, чтобы «что видно» и «что можно оценить» не
расходились:

- `feed_item_visible(user_id)` — публикация в статусе `normalized`/`processed` и её
  источник включён в `user_sources` этого пользователя;
- `standalone_feed_item_visible(user_id)` — то же плюс отсутствие строки в
  `cluster_items`;
- `cluster_visible(user_id)` — хотя бы один участник кластера доступен пользователю;
  подписка на все источники кластера не требуется.

`PUT` для отсутствующей, недоступной или уже вошедшей в кластер публикации, а также
для недоступного кластера возвращает `404` с одинаковым сообщением — причины отказа
не раскрываются. `GET` и `DELETE` собственной прежней реакции работают и после
отключения источника: ранее записанная реакция не удаляется автоматически, но новое
`PUT` для ставшей недоступной карточки не допускается.

Это проверка **возможности показа**, а не факт показа карточки на экране: учёта
показов в ITD-89 нет, и ответ API не считается фактом просмотра.

## Конкурентность

Запись (`PUT`) и удаление (`DELETE`) выполняются в одной транзакции:

1. `SELECT users.id ... FOR UPDATE` — блокировка строки пользователя (как
   `_lock_user` в `app/services/user_interests.py`), существование проверяется здесь же;
2. проверка доступности единицы;
3. чтение текущей реакции и вставка либо обновление той же строки;
4. `commit`; на ошибке — `rollback`.

Такая блокировка идемпотентна без `INSERT ... ON CONFLICT` и сериализует
одновременные `PUT` одного пользователя: дубликатов и нарушений `UNIQUE` нет, первый
запрос получает `201`, последующий — `200`. Допустима семантика последней успешно
зафиксированной операции, а не порядка прихода запросов. Внешних HTTP/AI-вызовов
внутри транзакции нет.

## Контракт для будущей персонализации

`app/services/feedback.py` — программный интерфейс:

- `set_feedback(session, user_id, kind, unit_id, reaction)` — создать или заменить
  реакцию, возвращает `(ответ, создана_ли)` для выбора `201`/`200`;
- `get_feedback(session, user_id, kind, unit_id)` — одна текущая реакция;
- `delete_feedback(session, user_id, kind, unit_id)` — снять реакцию;
- `list_feedback(session, user_id, kind=None, unit_ids=None, limit=20, offset=0)` —
  список реакций и групповой запрос по ID видимых карточек;
- `read_reactions(session, user_id, pairs)` — текущие реакции по смешанным парам
  `(kind, unit_id)` одним запросом к БД, без N+1.

Значения фиксированы: `useful` — положительный сигнал, `not_interested` —
отрицательный, отсутствие записи — **сигнала нет**, а не отрицательная реакция.
Вес реакции, пересчёт оценок и задачи Celery этой задачей не вводятся.

Если публикация позднее становится участником кластера, её сохранённая реакция
**не является** реакцией на новый кластер: автоматического переноса и объединения
оценок нет — политика миграции сигнала относится к следующему этапу.

## Проверки

Из `backend/`:

```bash
uv run ruff check .
uv run pytest tests/test_feedback_api.py tests/test_feed.py
ITD89_TEST_DATABASE_URL=<URL отдельной itd89_feedback_test... БД> \
  uv run pytest tests/test_feedback_postgres.py
```

Тесты API работают без живой БД. Адресные PostgreSQL-тесты выполняются только с
`ITD89_TEST_DATABASE_URL` на одноразовую БД `itd89_feedback_test*` и проверяют
upgrade/downgrade/reupgrade миграции `0012_feedback`, XOR/enum/UNIQUE/FK/CASCADE,
конкурентные `PUT` и `PUT`+`DELETE`, правила доступности, изоляцию пользователей и
отсутствие N+1 в групповых чтениях. Рабочая база не используется; без переменной
эти тесты пропускаются.
